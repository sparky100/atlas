# Capture fixtures

SPEC-capture.md §12: "the pipeline is done when it passes this, not when the
UI looks right." Each subdirectory here is one fixture — a real input file,
a real (small) pre-existing model, and a hand-verified expectation, run
through `runCapture()` (the same function the `capture-run` edge function
will call, PR12) with a `RecordedLlmClient` in replay mode. `src/capture/fixtures.test.ts`
turns every fixture into two real Vitest cases (§12.4's own "the fixtures
*are* the test"), gated into `pnpm test`, so a regression in a later PR that
breaks any fixture here fails the ordinary suite immediately.
`scripts/scoreCapture.ts` (`pnpm capture:score`) runs the same fixtures
through the same scorer for a human-readable report.

Sizes here are deliberately smaller than §12.2's own illustrative row counts
(12, 18, 60, …) — every named messiness dimension is still exercised, just
at a size a person can check by hand in a few minutes. A few fixtures also
use header text or cell values that differ from §12.2's own literal
examples where the *already-shipped* `columnSynonyms.ts`/`normaliseValue.ts`
tables (built in earlier PRs) don't recognise the spec's own example
verbatim (e.g. `columnSynonyms.ts` has no `Service area` → `capability`
entry, only `Service`; `parseDate` has no `Mon-YY` hyphenated format). Each
such adaptation preserves the *behaviour* being tested and is called out in
that fixture's own `input.csv`/generation script — it is never a reason to
weaken what the fixture actually checks.

## Anatomy of a fixture

```
NN-fixture-name/
  input.csv | input.xlsx    the document — an .xlsx/.pdf is generated by a
  | input.pdf | input.txt   small throwaway script using the `xlsx`/`pdf-lib`
                             package; see the git history of this directory
                             for the generation scripts used to build
                             02/06/07/08/09; they are not checked in, since
                             the binary file itself is the fixture, not the
                             script. `input.txt`/`input.csv` are plain text,
                             checked in directly.
  model.json                pre-existing model state: `{ elements, relationships?, aliases? }`,
                             each element/relationship keyed by a short
                             `key` string (never a bare UUID) that
                             `expected.json` references via `matchElement`/
                             `matchFrom`/`matchTo`. `loadFixture.ts` folds
                             this into a real `Head` via `element.create`/
                             `relationship.create` deltas (plus optional
                             per-attribute `overrides` for controlling a
                             specific fact's own confidence/date, e.g. to
                             test §4.4's conflict-strength rule) — never a
                             hand-built `ElementsHeadRow[]` shortcut.
  options.json               `{ inputKind, format, documentDate, reimportOf? }`
  previous.json (optional)   hand-authored `PreviousCandidateForDiff[]` —
                             §9.2's "synthetic previous job", read when
                             present (see fixture 03)
  expected.json              `ExpectedOutcome` (`fixtures/expectedOutcome.ts`)
  llm/{hash}.json (optional) `RecordedLlmCassette`s, keyed by `hashLlmRequest()`
```

## Adding a fixture

1. Write `input.csv`/generate `input.xlsx`, `model.json`, `options.json`,
   and a minimal `expected.json` (`{"job":{"status":"parsed"},"candidates":{},"absent":[]}`).
2. Run it once through `runCapture()` directly (a throwaway `tsx` script
   works well — `loadFixture(root, id)` gives you everything `runCapture`
   needs) and inspect the real output. If a needed LLM call throws
   (`RecordedLlmClient: no cassette for request hash "…"`), the hash is in
   the error; that is the file name for the next step.
3. For a needed cassette: re-run the same script with a *capturing*
   `LlmClient` (log the request via `hashLlmRequest()`, return a placeholder
   response) to see the exact prompt, then hand-write the real response and
   save it as `llm/{hash}.json` (`{text, stopReason: 'end_turn', inputTokens, outputTokens, cacheReadTokens}`,
   `text` being the schema's own JSON string).
4. Once the real run looks right, write `expected.json` for real — every
   candidate you want checked, keyed by its own `row_key`, plus anything
   that must be `absent`. Add the fixture id to `FIXTURE_IDS` in
   `fixtures.test.ts` and to nothing else (`scoreCapture.ts` discovers
   fixtures by directory listing).
5. Run `pnpm vitest run src/capture/fixtures.test.ts -t "<fixture id>"` until
   it's green, then `pnpm test` for the whole suite.

| 06 | sheet-type inference from a parent column; cross-sheet parent resolution; container context isolation (same module name under two different parents never cross-matches); `PARENT_UNRESOLVED` |
| 07 | header detection past a merged banner row; a totals row and blank rows mid-table; the date-parsing table (`AMBIGUOUS_DATE` for a month/bare-year, no warning for an ordinary dd/mm-vs-mm/dd swap); `MULTI_VALUE_CELL`; `FORMULA_ERROR` |
| 08 | `pdf-catalogue` — multi-page PDF: a title page, a repeating-header/footer table of applications, then narrative pages naming `flows_to`/`owns` facts, including one system (`Data Warehouse`) that only exists as a flow target, never a table row — the model has to infer it as its own element from context alone. **No recorded cassette** (PR13's own disclosed gap — see below); `pnpm test`/`pnpm capture:score` skip it (`SKIP`, not a failure) until a live run records one |
| 09 | `scanned` — an image-only-shaped PDF (every page under the 20-char threshold); `NO_TEXT_LAYER` at parse, before any LLM call at all — fully replay-tested, no cassette needed |
| 10 | `pasted-notes` — short free-text meeting notes; multiple facts (`vendor`, `plannedEnd` from "Q2 2027", `lifecycleStatus` from "goes live") extracted from one short passage each; `owns` to an actor already on main; an explicit non-statement ("nobody could say who owns…") correctly produces no `owns` edge |

## Fixtures 08 and 10: what "real cassette" means here, and why 08 doesn't have one

Every fixture's own `llm/*.json` cassette (01-07 included) is **hand-authored**,
never literally recorded from a real Anthropic call — `RecordedLlmClient` is a
test double for the network (CLAUDE.md rule 7), not a claim that a real model
produced this exact text. For prompt A/C (narrow, closed-vocabulary
classification over a handful of columns or a fixed capability tree) a
hand-authored response is a faithful stand-in: there's little room for a real
model to reasonably disagree.

Prompt B (prose extraction) is different in kind, not just size — recognising
which entities and relationships a paragraph of free text actually states is
exactly the open-ended judgement call this pipeline exists to get right, and
it's also §12.6's whole reason for a *live* evaluation mode to exist at all.
Fixture 10's own text is short and fully specified in SPEC-capture.md §12.2's
own table, so a hand-authored cassette for it can be written with real
confidence about what a competent extraction looks like — it's shipped here,
replay-tested, gated into `pnpm test`. Fixture 08's own 6-page catalogue is
not: hand-authoring "what the model would say" about a much larger, messier
document would test nothing about real model behaviour, only about whatever
the fixture's own author assumed — so it ships with a real PDF and a real,
reasoned `expected.json`, but no cassette, honestly `SKIP`ped by the replay
suite until `pnpm capture:score --live` (§12.6, needs `ANTHROPIC_API_KEY` or
a configured proxy) records one for real and it's reviewed into `llm/`.

Fixture 08 is also smaller than SPEC-capture.md §12.2's own illustrative
"26 systems across pages 2-7 of 9" — 6 systems across 3 table pages of 6
total — so it does not exercise cross-chunk endpoint resolution (everything
fits in one ~12,000-char prompt-B chunk); that behaviour is already covered
at the unit level by `src/capture/chunk.test.ts`. Same size-reduction
disclosure as every other fixture here, just for a size §12.2 itself allows
to be irreducibly large (it's one of the two fixtures — with 07 — the table
excuses from the "10-40 rows" rule).
