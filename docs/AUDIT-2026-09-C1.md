### 1.4 CI: the `e2e` job's history and the fps numbers

**Workflow:** GitHub Actions workflow `CI` (`.github/workflows/ci.yml`, workflow id `351386984`), jobs `lint`, `typecheck`, `unit-test`, `build`, `database`, `e2e` ("Playwright smoke (UI Definition of Done)"), `deploy-migrations`.

**Live run history queried via `mcp__github__actions_list`/`actions_get`** (47 runs returned for `ci.yml`, covering `2026-09-06T06:52` through the run for this session's own HEAD commit at `2026-09-07T06:54`):

- The **last run where the whole workflow conclusion was `success`** is run `34021157937` (commit `30562aa2`, `2026-09-06T08:11:17Z`). At that point in the workflow's history it had only 4 jobs — `lint`, `typecheck`, `unit-test`, `database` — no `e2e`/`build` job yet existed. This commit predates **all** of Sprint H1's 12 items and all of Sprint C1: **no fully-green CI run has ever covered any Sprint H1 or Sprint C1 change.**
- Every one of the 47 runs sampled from `34022079727` (commit `5078670f`, `2026-09-06T08:31:18Z`) onward has workflow conclusion `failure` or `cancelled` — none `success` — including the run for this session's own HEAD (`34092892156`, commit `2a0d894a`, `2026-09-07T06:54:09Z`).
- **`lint`, `typecheck`, `unit-test`, `build` pass on every run sampled**, including the most recent one — the repeated overall `failure` conclusion is caused entirely by `database` and/or `e2e`.
- **The `e2e` job has never once reached `success`** in any run this audit inspected. Two distinct failure modes were observed at different points in its history, both confirmed by directly fetching job logs:
  - **Mode A — the job never starts the app at all:** at commit `89fba771` (run `34035733159`, job `101493332966`, `2026-09-06T13:19-13:24`), `Start local Supabase` and `Apply all migrations` and `Install Playwright's browser` all **succeeded**, but `Run Playwright tests` failed after exactly 60s with `Error: Timed out waiting 60000ms from config.webServer.` — the exact failure `playwright.config.ts`'s own module comment (and H1 item 11's fix) describes, and it recurred here.
  - **Mode B — Supabase itself never starts:** at commit `69a75739` (run `34065020469`, job `101572146686`, `2026-09-06T22:47`) and again at this session's own commit `2a0d894a` (run `34092892156`, job `101649975146`, `2026-09-07T06:54-06:56`), the very first step, `Start local Supabase`, failed outright (after ~2 minutes), and every later step was skipped.
  - The `database` job shows the same two-mode pattern on the same runs (e.g. `34065020469`'s `database` job also fails at `Start local Supabase`; `34035733159`'s and `34022079727`'s `database` jobs instead got past Supabase startup and failed later, at `Run integration tests`).
- **Conclusion: the `e2e` job (and, on most runs, the `database` job with it) has never passed for any Sprint H1 or Sprint C1 commit.** `.github/workflows/ci.yml`'s own inline comment already states one contributing cause ("Sprint H1 fix: ... `tr -d '"'` ... This is why the `database` job has never once passed") — the live run history confirms the job kept failing afterward too, for the second, independent reason (Mode B, Supabase/Docker never starting in the runner) that H1's fix did not address.

**fps numbers:** `e2e/landscape-perf.spec.ts:174-175` asserts `p50 fps ≥ 55` and `p5 fps ≥ 45` — these are **written thresholds in the test's own `expect(...).toBeGreaterThanOrEqual(...)` calls, not numbers recorded from any run.** Because the `e2e` job has never gotten past its `Run Playwright tests` step without failing first (per the two failure modes above), **no fps number has ever been produced by any CI run for this test, at any commit sampled.** This matches `docs/AUDIT-2026-09-U2.md:836`'s own finding for the local authoring sandbox ("≥55/≥45 are written thresholds, not observed results... The only place this assertion has a chance to produce a real number is CI's `e2e` job") — that statement remains true today, now independently confirmed against the job's actual live run history rather than only the sandbox's own inability to run it. The companion payload-size test in the same file (`e2e/landscape-perf.spec.ts:32-52`, needs no browser or database) is the one perf-adjacent number that has actually been measured: `~8.45 MB` for a single-element edit against a 2,010-element/6,000-relationship/~16,000-fact model, against a 12 MB budget (comment at `e2e/landscape-perf.spec.ts:44`, corroborated by `docs/SPEC-data-model.md:1331`).

## 2. C1 data path

Six actions, UI to rows written. "Security definer: yes/no" is read directly off each function's `create or replace function` statement in its migration file.

### 2.1 Create change

`src/ui/changes/ChangesView.tsx:47` (form submit) → `src/ui/changes/useChanges.ts:66` `createChange` → `src/db/branches.ts:35` `createChangeBranch` → **plain PostgREST `insert` into `branches`, no RPC**. Authorization is entirely the `branches_insert` RLS policy (`supabase/migrations/20260906071400_history.sql:282-297`), which itself calls `atlas.has_role` (`20260906071200_tenancy.sql`, `language sql stable security definer`).

Rows written: one `branches` row (`kind='change'`, `status='draft'`, `base_commit_id = head_commit_id = main`'s current head, `title`, `description`, `target_date`, `created_by`).

### 2.2 Edit in branch

`src/ui/routes/ElementPage.tsx` (Edit → Save) → `src/ui/elements/useElementEditor.ts:109` `save()` → `src/db/commits.ts:118` `commitToBranch` → RPC `commit_deltas`.

**`atlas.commit_deltas`** (current definition `supabase/migrations/20260906161000_merge_review_queue.sql:137-238`) — **security definer: yes** (`language plpgsql security definer`, line 154). Re-derives role and `author_id` from `auth.uid()`, never trusts the client. Inserts one `commits` row and one `deltas` row per changed attribute; `update branches set head_commit_id = p_commit_id` (line 224, inside the same function, guarded by the `atlas.guard_branch_head_advance` trigger on `branches`); materialises `elements_head`/`relationships_head`/`facts` only `if v_branch_kind = 'main'` (never for a `change` branch — §1.2 item 17 above).

Rows written (change branch case): `commits` (one row), `deltas` (one row per field), `branches.head_commit_id` advanced. No projection tables.

### 2.3 Refresh (rebase)

Two UI entry points, one shared write path:
- Pre-review: `src/ui/reviews/BranchRebasePanel.tsx` → `src/ui/reviews/useBranchRebase.ts:80` `pushRebase`.
- Mid-review: `src/ui/reviews/ReviewRequestView.tsx` → `src/ui/reviews/useReviewRequest.ts:137` `pushRefreshAndResubmit`.

Both call `src/db/mergeRequests.ts:187` `pushRefresh`, which:
1. Refuses (C15, `unresolvedFieldConflictKeys`, `src/engine/mergeResolution.ts:64-67`) if any FIELD_CONFLICT key has no staged resolution.
2. If any choices are staged: mints a `merge_resolution` `sources` row (`createMergeResolutionSource`, `src/db/sources.ts:48`, plain insert, RLS-gated by `supabase/migrations/20260906162100_merge_resolution_source.sql`), builds resolution deltas + `resolved_conflicts` entries (`src/engine/mergeResolution.ts:83-135`).
3. Builds a `kind: 'merge'` `CommitEnvelope` (`parentCommitId = branch.head_commit_id`, `mergedBranchHeadCommitId = main's current head`) and calls the **same `atlas.commit_deltas` RPC as §2.2**, this time with `p_resolved_conflicts` populated.

The mid-review path additionally recomputes the classification and calls `resubmitMergeRequest` (`mergeRequests.ts:105`) → RPC `atlas.resubmit_merge_request` (`supabase/migrations/20260906162000_resubmit_merge_request.sql:14-56`, **security definer: yes**, line 17).

Rows written: `commits` (one `kind='merge'` row), `deltas` (one per resolved field conflict), `resolved_conflicts` (one per resolution), `sources` (one `merge_resolution` row if any resolutions), `branches.head_commit_id` advanced. **`branches.base_commit_id` is not written by any step of this path** — see §5.3 below; this is a significant, independently-confirmed drift from what ADR-005's amendment and SPEC S-11 both state should happen. If invoked mid-review: also `merge_requests` (`status`, `requested_head_commit_id`, `main_head_commit_id`, `classification`).

### 2.5 Split

**Missing.** Exhaustive search (`grep -rn "split_from\|split_branch\|splitBranch" src/ supabase/`) finds:
- The schema: `branches.split_from` column, its FK to `branches(id)`, a `check (split_from is null or kind = 'change')`, and an index — `supabase/migrations/20260906160000_branches_change_metadata.sql:13-27`. **No `grant update (split_from)` exists anywhere** — a client cannot write this column even directly; only `title`, `shared_for_review`, `description`, `target_date`, `head_commit_id` have any authenticated column grant on `branches`.
- The type: `split_from: UUID | null` on `BranchRow` (`src/db/types.ts:70`).
- Two read-only helpers: `listSplitBranches`, `resolveChangeLineage` (`src/db/branches.ts:111-135`) — both plain selects.
- A read-only "Delivered / remaining" panel in `src/ui/changes/ChangeView.tsx` that renders whatever `resolveChangeLineage` returns (always empty today, since nothing ever creates a split).
- **No SQL function** (`atlas.split_branch` or equivalent) anywhere in `supabase/migrations/`.
- **No UI action or button** anywhere in `src/ui/reviews/` that triggers a split; `grep` for "split"/"partial" in `ReviewQueueView.tsx`/`ReviewRequestView.tsx` returns nothing.
- **No dependency-closure algorithm** anywhere in `src/engine` (`grep` for "closure" returns only two module comments — `src/engine/mergeResolution.ts:19-23`, `src/db/mergeRequests.ts:9-16` — both naming the cascade as unbuilt, not implementing it).
- `src/db/repository.integration.test.ts:854-896`'s only "split" test inserts a `split_from` row via a **raw SQL insert** for test purposes, with its own comment (lines 875-878) stating this stands in for "a future `atlas.split_branch`."

This is disclosed, not silent: `docs/SPEC-data-model.md:868` states plainly, "Partial merge (ADR-006 amendment's split-into-a-new-branch) is likewise not built this step; `atlas.merge_branch` always merges the branch's entire head."

### 2.6 Merge

`ReviewRequestView.tsx` "Merge" → `useReviewRequest.ts:213` `merge()` → `src/db/mergeRequests.ts:139` `mergeApprovedRequest`, which folds `branch.head_commit_id` fresh from genesis (`foldFromGenesis`, full replay — never reads a projection table), serializes it, and calls RPC `atlas.merge_branch`.

**`atlas.merge_branch(p_merge_request_id, p_commit_id, p_message, p_elements_head, p_relationships_head, p_facts, p_head_hash)`** — `supabase/migrations/20260906161000_merge_review_queue.sql:439-507`. **Security definer: yes** (line 450). Checks role (owner/architect only) and request status `='approved'`; re-checks `atlas.branch_reaches_commit` — if false, **resets** `merge_requests.status='pending'`/`branches.status='proposed'` and returns `null` (a deliberate non-error, so the reset itself isn't rolled back — comment lines 430-438) rather than raising; on success, delegates the actual write to the **same `atlas.commit_deltas` RPC as §2.2** (`p_branch_id => main.id, p_kind => 'merge', p_merged_branch_head_commit_id => branch.head_commit_id`), then sets `merge_requests.status='merged'`/`merge_commit_id` and `branches.status='merged'` (the merged branch is never deleted).

**Garbage-collected base commit:** cannot occur. `commits`/`deltas` have no delete grant/policy for any role (`grant select, insert` only — `supabase/migrations/20260906071400_history.sql:358,387`); `atlas.merge_branch`/`mergeApprovedRequest` fold from `commits`/`deltas` directly (`buildCommitLoader`, `src/db/commitLoader.ts:32`, unconditionally fetches every commit/delta for the model), never from the `elements_head`/`relationships_head`/`facts` projection cache — the only thing ever pruned (`atlas.replace_main_head_projection`, deletes a *superseded, untagged main head's projection rows*, never a `commits`/`deltas` row).

## 3. Invariants

| # | Invariant | Test name(s) | Verdict |
|---|---|---|---|
| 1 | `main.head == fold(deltas)` after any C1 sequence | `verifyHeadMatchesFold` (`src/engine/head.ts:224`) is tested only by `'verifyHeadMatchesFold reports ok for a correctly computed head, and catches a tampered one'` (`src/engine/head.property.test.ts:241`) — a synthetic, hand-built commit graph, **not** a real create→edit→refresh→review→merge sequence run through the actual RPCs. ### 5.3 ADR-005's refresh amendment (`base_commit_id` moves on refresh) — **not matched by code**

ADR-005's Sprint C1 amendment (`docs/ADR-000-foundations.md:150`) and SPEC S-11 (`docs/SPEC-data-model.md:27`) both state, in near-identical language, that a refresh moves `branches.base_commit_id` to main's new head, keeping it equal to `mergeBase(B)` so that folding at `base_commit_id` is a valid O(1) shortcut for As-is.

**This is not what the code does.** `grep -n "base_commit_id" supabase/migrations/*.sql` shows `base_commit_id` written exactly once — at branch creation (`src/db/branches.ts:43`, `createChangeBranch`'s insert) — and every later occurrence of `p_base_commit_id`/`base_commit_id` in `atlas.commit_deltas` (`supabase/migrations/20260906161000_merge_review_queue.sql:141,173,176,198,228`) is the **new commit's own `parent_commit_id` parameter**, not an update to the `branches` row's `base_commit_id` column. No migration, function, or trigger anywhere ever runs `update branches set base_commit_id = ...`. Confirmed by reading `atlas.guard_branch_head_advance` in full (`supabase/migrations/20260906071800_branch_head_advance.sql:15-41`) — it validates `head_commit_id` advancement only, and touches no other column.

This has a real functional consequence, not just a documentation mismatch: two production consumers read `branch.base_commit_id` directly as a stand-in for `mergeBase(B)`, per the ADR-005 amendment's own stated rationale:
- `src/db/branchProjection.ts:93`, `resolveBranchModeProjection` — `const asIsHead = foldFromGenesis(branch.base_commit_id, loader)` — the As-is/To-be/Diff selector's As-is lens on every canvas.
- `src/db/changeSummary.ts:134,142` — the change page's "Deltas on this change" list forks at `branch.base_commit_id`.

After a refresh, both of these fold from the **original fork point**, not the branch's actual current merge base — showing stale As-is content and a stale own-deltas list, since `base_commit_id` never advanced. The merge/review pipeline itself is unaffected: `computeMergeReview`/`threeWayDiff` (`src/engine/branch.ts`) compute `mergeBase(B)` via a live DAG walk on every call and never read `branch.base_commit_id` — so approval/merge correctness (and SPEC's own P-16/P-17) hold regardless. No code comment anywhere in the C1-era refresh path (`src/db/mergeRequests.ts`, `src/ui/reviews/*`) acknowledges this gap; it was not found flagged in any doc prior to this audit.

### 5.4 Identity "keep both" dismiss does not persist — **contradicts SPEC §7.4 and P-18**

SPEC §7.4 (`docs/SPEC-data-model.md:862`) and P-18 (`docs/SPEC-data-model.md:1293`, "dismissing one persists in `classification` and it is not raised again for the same pair") both specify that dismissing an identity warning is recorded server-side. The actual implementation — `src/ui/reviews/useReviewRequest.ts:74,113,117` and `src/ui/reviews/BranchRebasePanel.tsx:41` — stores dismissals in a plain `useState<Set<string>>`, never written to `merge_requests.classification` or any table. A page reload, or a second reviewer opening the same request, sees the warning again. `src/ui/reviews/ReviewRequestView.tsx`'s own comment (line 33 area) states this is a session-local dismiss, correctly self-disclosed in code comments, but this self-disclosure was not carried back into SPEC/ADR text, so SPEC §7.4/P-18 still describe the undone, persisted version as if it were current behaviour.
