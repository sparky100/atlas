## Reading this

- "resolve→paint" is almost entirely client-side (route match + the
  loading shell's own render) — a regression here points at bundle size or
  a render-blocking import, not the network.
- "paint→data" is this route's own data fetch — this is what E8 item (1)'s
  shared data layer (org/model/branches/head/profiles cached once, not
  re-fetched per page) and item (2) (main reads the projection, never
  folds) are meant to shrink.
- The action table's wall-clock time bundles the commit round-trip and
  today's full-reload-on-commit pattern (`reload()` re-runs every fetch
  from scratch — see `CapabilityMapPage.tsx`'s own `reloadAll`) — E8 item
  (3)'s "apply the returned deltas to the cached head and re-render, then
  revalidate in the background" is what should shrink this number
  specifically, without touching the commit itself.

## Item (5) — realtime resync audit

"Realtime resync only on relevant events" assumes an existing resync
mechanism is firing too broadly. Auditing every `supabase.channel(...)`
call in `src/` before touching anything found the opposite: there is
exactly one **live** Realtime subscription in the running app, and it
was already scoped correctly.

- **`useBranchStatusReset.ts`** (mounted once, at the app root, via
  `SelectedRefProvider.tsx`): one channel per currently-selected branch,
  `postgres_changes` UPDATE on `branches` with a server-side
  `id=eq.${branchId}` filter — not a client-side re-filter of a wider
  event stream. Its handler is fully targeted: it reads `payload.new.status`
  and, only when the branch left `draft`, resets this tab's selected ref
  back to main. No refetch, no cache invalidation, no broader resync of
  any kind. Nothing here needed narrowing.
- **`src/db/realtime.ts`'s `subscribeToModelChannel`** (per-model commits/
  comments channel, three separately-filtered `postgres_changes`
  subscriptions plus a presence sync): well-designed the same way — each
  filter is scoped to the one model, and its `onCommit`/`onCommentInsert`/
  `onCommentUpdate` callbacks hand the caller the specific changed row
  rather than triggering a refetch; `onResync` (a real, if narrow,
  "resync" in the item's own sense) fires only once per actual reconnect,
  not per event. But **this function has no caller anywhere in `src/`
  outside its own integration test** — dead code, not wired to any live
  page. `docs/AUDIT-2026-09-12.md`'s own M1a entry already flagged this
  gap independently.

Nothing here needed the change item (5) describes: the one live
subscription already resyncs only on the relevant event, and the other
realtime code isn't live at all — activating it would be a real feature
(live-updating comment counts/commit lists), not a performance fix, and
out of scope for this sprint. No code changed for this item; closed as
already satisfied.
