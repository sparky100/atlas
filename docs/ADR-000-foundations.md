# ADR-000: Foundations

**Status:** Proposed
**Scope:** Atlas — an enterprise-architecture product for mid-market and public-sector organisations (councils, NHS boards, housing associations, universities), sized for one-or-two-architect teams currently on Sparx, Visio, or spreadsheets.

This document is a set of numbered architecture decisions (ADR-001 through ADR-019). Each follows Context / Decision / Alternatives Rejected / Consequences. It is a foundations record, not a full design — several decisions explicitly defer detail to a future ADR, and say so.

**Working assumptions**, stated up front because several decisions depend on them:

- The product name used throughout is **Atlas** (the repository's own name), pending an actual brand decision.
- The brief's own use of "RLS" is read as a signal that the backend is Postgres (plausibly Supabase, given the tooling available in this environment). Row-level security, `organisation_id` columns, and `jsonb` attributes are chosen on that assumption. If the real backend differs, ADR-009 and the attribute-storage half of ADR-001 need revisiting first.
- "Existing suite" refers to a sibling product family this document cannot inspect directly (out of this session's repository scope). ADR-014's package-boundary decision is therefore necessarily provisional on one point, which it names explicitly.

## Preface: pushback on the brief

The brief is good and mostly implementable as stated, but a few things are wrong or underspecified enough to call out before the decisions below, since several decisions resolve them by disagreeing with the brief:

1. **"External" should not be its own element type.** Making it a sibling of System/Container/Actor doubles the attribute sets and the `relationship_type_rules` matrix for no new modelling power — an external system is a system, plus one fact ("we don't own it"). ADR-001 makes it an attribute instead.
2. **"Contains" should not be a relationship type.** Structural decomposition (capability→capability, system→container) needs single-parent and acyclic guarantees. Modelled as generic edge rows, nothing stops two parents or a cycle without extra application code; modelled as a foreign key on the child, the database enforces it. ADR-001 treats containment as structure, not a fact-relationship.
3. **"Versions (immutable tagged snapshots)"** reads as if a version is a stored copy of the whole landscape. It should be an immutable *pointer* (a tag on a commit), not a duplicated materialisation — otherwise every tag doubles storage and creates a second place state can drift from. ADR-002/003 make tags pointers; a snapshot cache is a separate, disposable performance optimisation.
4. **Capture pipeline, merge review queue, and decisions-with-evidence are requirements but weren't in the "cover at minimum" list.** They're core to the thesis ("capture with smart merging plus changes as branches plus decisions with arguments"), so this document adds ADR-004, ADR-006, and ADR-013 for them rather than leaving them implicit inside the delta model. Their omission from the minimum list looks like an oversight, not a deliberate v1 cut.
5. **Watch for a "Service" type request.** Public-sector customers (LGA service lists, NHS service directories) will very likely ask for a citizen-facing "Service" layer distinct from Capability within the first few months. Recommend *not* adding it now — model it as a tag/subset of leaf capabilities — but flag it here so it isn't treated as a surprise later.
6. **Maturity/heat-map scoring is explicitly out of scope for v1.** It's one of the most common ways EA tools accumulate scope; the brief doesn't ask for it and this document doesn't add it. If it's added later, ADR-007's fact model already has a natural home for it (a rated fact on a capability, sourced like any other).
7. **"One or two architects" per organisation is a role-model constraint, not just a target market.** ADR-009's roles must degrade to "one person, all rights" without friction — a four-role RBAC that assumes separation of duties will feel bureaucratic to the exact customer this product is for.
8. **The brief is silent on identity/tenancy overlap with the existing suite.** ADR-014 flagged this as the one open question this document could not close from inside this repository at the time it was written; ADR-017 closes it (Atlas has its own project and its own identity/tenancy tables, permanently).

## ADR-001: Element and relationship taxonomy

**Context.** The taxonomy has to stay small on purpose (per the stated philosophy) while covering landscape → context → container plus one business layer (capability) — originally one level deeper still, container → component, until S1 item 18 removed the component level (see that amendment below). It has to support AI-assisted capture (which needs per-type validation to score confidence against) and must not let "just one more field" turn into scope creep.

**Decision.**

*Element types (four, not five):* **Capability, System, Container, Actor** (subtype `person` or `team`, joined by `organisation` per S1 item 11a's own amendment below — kept as one type with a subtype rather than several, because all three can be relationship endpoints for `owns`/`uses` interchangeably, and splitting them would multiply `relationship_type_rules` rows for no semantic gain). A fifth type, Component, existed until S1 item 18 removed it (see that amendment below).

"External" is not a type. It is an attribute (`is_external` boolean, `external_organisation` nullable text) available on System, Container, and Actor.

Attributes are stored as a discriminated single table per superclass (`elements`, `relationships`) with a `type` column and a `jsonb` attribute payload, validated against a versioned `type_schemas` registry (`type_schemas`: `type`, `schema_version`, `json_schema`, `effective_from`). This is deliberately not one table per element type, and not a fully generic EAV model — see Alternatives Rejected.

Structural containment is **not** a relationship row. It is a plain foreign key on the child element: `parent_capability_id` on Capability, `parent_system_id` on Container. Single parent and acyclicity are then ordinary database/application constraints, not something a generic edge table has to be taught to enforce.

Ownership is never a foreign-key attribute on an element (e.g. no `owner_actor_id` column). It is always the `owns` relationship, so *when* ownership changed and *from what source* is itself a fact with provenance (ADR-007), not a silently-overwritten column.

Attribute sets per type (required fields marked *req*):

| Type | Key fields |
|---|---|
| Capability | `name` *req*, `description`, ~~`level` *req* (1–3)~~ (ADR-016: computed from `parent_capability_id` depth, not a stored attribute), `parent_capability_id`, `code` (ADR-020, amended from "reference code from a starter map": an organisation's own optional reference, never populated by seeding), `template_ref` (nullable, links back to `capability_map_template_items`) |
| System | `name` *req*, `description`, `lifecycle_status` *req* (`planned`/`active`/`retiring`/`retired`), `vendor`, `is_external`, `external_organisation`, `introduced` (date, when it went live), `planned_end` (date, planned decommission — independent of `lifecycle_status`; a system can have a known end date well before it actually reaches `retired`) |
| Container | `name` *req*, `description`, `technology`, `parent_system_id` *req*, `is_external`, `introduced`, `planned_end` |
| Actor | `name` *req*, `subtype` *req* (`person`/`team`/`organisation` — S1 item 11a), `email` (person only), `org_unit`, `is_external`, `external_organisation` |

*Relationship types (four, non-structural only):* **supports** (System → Capability), **uses** (System/Container → System/Container, directional runtime dependency; Actor → System/Container per S1 item 11a's own amendment below), **owns** (Actor → Capability/System, accountability), **flows-to** (System/Container → System/Container, integration/data flow; attributes `data_classification`, `protocol`, both optional).

A `relationship_type_rules` table constrains what's legal: columns `relationship_type`, `allowed_source_types` (array), `allowed_target_types` (array), `max_cardinality_per_source` (nullable — e.g. `owns` may cap at one *primary* owner without forbidding secondary owners). This is the enforcement point that stops nonsense like "Actor uses Capability."

*(Sprint H1 amendment.)* This constraint shipped as `RELATIONSHIP_TYPE_RULES`, a constant in `src/contracts/relationshipTypeRules.ts` (SPEC-data-model.md §3.3), rather than as a migrated table — see that section's own note for why. `src/engine/deltas.ts`'s `apply()` checks every `relationship.create` against it, so "Actor uses Capability" is now a rejected commit, not just a documented intention.

*Explicit non-types* — deliberately excluded from the taxonomy, named here so a future feature request has to argue against a written decision rather than just accreting: business processes/workflow steps (BPMN-shaped), logical data entities (ERD-shaped), infrastructure/network topology (racks, subnets, firewalls), projects/programmes as landscape elements (a programme is the subject of a change branch's metadata, not a landscape fact), goals/strategy/KPIs (a layer above capability), requirements/user stories, cost/budget figures, risk register entries, service-catalogue entries (see Preface #5), maturity/heat-map ratings (see Preface #6), and org-chart reporting lines beyond a flat Actor.

**Amended (Run cost, `annualRunCost` — the argument this list asks for, recorded rather than skipped).** "Cost/budget figures" above excludes cost as an *element type* and unformatted cost figures as modelled facts; it does not exclude a banded cost *judgement* recorded as an ordinary attribute on types this ADR already defines. `SystemAttributes` and `ContainerAttributes` gain one optional field, TS-contract-only like Prompt 7k item 1's own three (no migration — `elements_head.attributes` is `jsonb`): `annualRunCost: 'none_included' | 'under_50k' | '50k_250k' | '250k_1m' | '1m_5m' | 'over_5m'` — the avoidable annual run cost of *that element* if it is retired, banded and judged, never a stored figure and never an allocation of a platform's cost. Unset means "Not entered", visibly distinct from the recorded `none_included` ("None / included") band — an unset fact is not a recorded one. Restricted to system/container structurally (the field simply doesn't exist on Capability/Actor/ValueStream, so `validateAttributeValue` rejects it there); deliberately not part of `effectiveModuleAttributes`'s inheritance set (a module's avoidable cost is its own judgement, not the platform's band), but it *does* carry over in `convertSystemToModule` (the same software's avoidable cost). **No engine rule, health finding or colour-by reads it** — its roll-ups (`src/ui/elements/annualRunCost.ts`) are display helpers over ordered bands: highest band and per-band counts, never a sum or average. Labels live in code (`attributeSchema.ts`'s `ANNUAL_RUN_COST_BANDS`, "keys stored, labels in code" per ADR-022); orgs cannot define a custom attribute over the same key (`isCoreAttributeKey`, refused by `createAttributeDefinition`).

**Amended (Capability importance).** "Maturity/heat-map ratings" above (Preface #6) excludes a blended, weighted, or computed score across capabilities — it does not exclude a single judged *ordering* attribute on one capability, used only to order a display, never combined with anything else into a score. `CapabilityAttributes` gains one optional field, TS-contract-only like `annualRunCost` above (no migration — `elements_head.attributes` is `jsonb`): `importance: 'low' | 'medium' | 'high'`, judged by the capability's own business owner or an architect. Ordered high-first — the *opposite* direction from every other ordered attribute this ADR defines, since its one consumer is a display sort (Director home's weak-capability tiles), never a worst-of roll-up (`src/ui/home/capabilityImportance.ts`'s own `IMPORTANCE_ORDER`). Unset means "not assessed", sorts last among weak tiles, never read as `'low'`. Restricted to Capability structurally (the field simply doesn't exist on System/Container/Actor/ValueStream, so `validateAttributeValue` rejects it there). Distinct from `essentialFunction` (Prompt 7k item 5, NIS/CAF): that is a regulatory fact with its own health finding; this is a judgement call with none. **No engine rule, health finding, or colour-by mode reads it** — its one consumer is Director home's own weak-tile ordering (`compareWeakTiles`, `src/ui/home/capabilityTileFit.ts`). Labels live in code (`attributeSchema.ts`'s `IMPORTANCE_LEVELS`, "keys stored, labels in code" per ADR-022); orgs cannot define a custom attribute over the same key (`isCoreAttributeKey`, refused by `createAttributeDefinition`).

**Amended (Disposition, TIME — F11, decided by the human 2026-10-02).** "Maturity/heat-map ratings" above (Preface #6) excludes a score; it does not exclude a recorded *decision about* a system. `SystemAttributes` and `ContainerAttributes` gain one optional field, TS-contract-only like `annualRunCost` and `importance` above (no migration — `elements_head.attributes` is `jsonb`): `disposition: 'tolerate' | 'invest' | 'migrate' | 'eliminate'` — Gartner's TIME vocabulary for what the estate intends to do with that system. It is a judgement someone made and owns, not a measurement and not a blend of other facts, so it doesn't breach the exclusion. Unset means "Not assessed", never read as `'tolerate'`. On a module (a platform's container) it is an optional **override that is not inherited**: absent on the module means the module has no disposition of its own, and nothing reads the platform's value in its place (unlike `effectiveModuleAttributes`'s five inherited fields) — a platform marked *Invest* can carry a module marked *Eliminate*, and a module with nothing recorded reads "Not assessed". It carries over in `convertSystemToModule` (the same software's disposition). Ordered `eliminate > migrate > tolerate > invest` for worst-of display roll-ups only (the capability map's disposition colour-by: worst disposition among a capability's supporting systems and modules). Unlike `annualRunCost`/`importance`, it **does** feed one health finding — "marked Migrate or Eliminate, with no open change retiring it" — because a recorded intention with no work behind it is exactly the kind of gap the architect door exists to show; and Portfolio shows where it disagrees with the recorded facts (e.g. *Invest* on a poor-fit system), never where an input is missing. Labels live in code (`attributeSchema.ts`'s `DISPOSITION_LEVELS`); orgs cannot define a custom attribute over the same key (`isCoreAttributeKey`).

**Alternatives rejected.**
- *Fully generic EAV/triple store for all attributes* — unqueryable at scale, no per-type validation to hang AI confidence scoring on.
- *One table per element type* — a migration for every new field, and joins across five tables for the most basic "search everything" query.
- *"External" as its own element type* — duplicates attribute sets and relationship rules for a single boolean fact's worth of information.
- *"Contains" as a generic relationship* — loses single-parent/acyclic guarantees that come for free from a foreign key.
- *Owner as a foreign-key column* — throws away the history and provenance of who owned something and since when.

**Consequences.** Adding a new element or relationship type is intentionally expensive (a schema entry, a migration, new `relationship_type_rules` rows) — that friction is the mechanism that keeps the taxonomy small, not an accident to be optimised away. Full validation (required fields, referential integrity, rule conformance) is enforced at materialisation time (ADR-003), not at write time, so a capture pipeline's draft branch is allowed to be temporarily invalid before human review.

**Amended (Prompt 7k item 2, owner roles, `supabase/migrations/20260911070000_owns_role.sql`).** `owns.primary: boolean` (Sprint U4-1's own generalisation of C17 to `owns`) is replaced by `owns.role: 'business' | 'technical' | 'service'` — a target can now have up to three live `owns` edges at once, one per role, rather than a single "the owner" flag with an unlimited number of unranked secondary owners alongside it. Cardinality moves from "at most one primary owner per target" to "at most one owner per `(target, role)`" (C17, `src/engine/deltas.ts`'s `checkPrimaryCardinality`; the DB backstop `relationships_head_one_owner_per_role` replaces `relationships_head_one_primary_owns_per_target`). `src/engine/merge.ts`'s `classifyMerge` — real, shipped code, not a future item — updates its own `structural:cardinality` detection the same way; `docs/ADR-021-structural-conflict-resolution.md` §4.3's not-yet-built "primary pick" design is updated to a "role pick" for `owns` (leaving `supports.role` untouched — a separate mechanism this decision doesn't touch), with an explicit open sub-question left for whoever implements it.

`OwnsAttributes.primary` is **not removed** from the contract — it stays, marked `@deprecated`, alongside the new required `role`. This is deliberate: `relationships_head`/`deltas` are never hand-edited to migrate existing data (see the new rule this amendment also adds, SPEC §6.8 — a data change is a real commit, never a row rewrite, because a row rewrite would silently revert on the next `rebuildHead`/`foldFromGenesis` replay and leave `commits.head_hash` permanently unreconcilable for every downstream commit). An existing `owns` edge keeps `primary` exactly as recorded, un-enforced by the new cardinality index (a `NULL` role never conflicts with anything in a partial unique index) until `src/db/backfillOwnsRole.ts` (run once per model, `pnpm backfill:owns-role`) writes a real `relationship.update` commit setting `role` from it and clearing `primary` — `primary: true` becomes `role: 'business'`, `primary: false` becomes `role: 'technical'` (there is no boolean value `primary` could ever have meant `'service'`, since that role didn't exist before this sprint).

**Amended (Prompt 7k item 1, criticality and hosting).** `SystemAttributes` gains three optional fields, all TS-contract-only (no migration — `elements_head.attributes` is `jsonb`, per rule 7's own "no schema change for an attribute-only addition" precedent): `criticality: 'critical' | 'high' | 'medium' | 'low'`, `hostingModel: 'on_premises' | 'private_cloud' | 'public_cloud' | 'saas' | 'hybrid'`, and `hostingProvider: string` (free text — deliberately not an enum, since real hosting providers are open-ended in a way on-prem/cloud/SaaS is not). Both `criticality` and `hostingModel` are optional and unrated until someone records them, the same "no fact without provenance" shape every other attribute in this taxonomy already has.

The two are deliberately treated differently by every colour-by/aggregate consumer, a judgment call recorded here so a later sprint doesn't have to re-derive it: `criticality` is **ordered** (`low < medium < high < critical`, `src/ui/elements/criticalityTone.ts`'s `CRITICALITY_ORDER`) and so supports a "worst-of" rollup — it gets both a capability-map colour-by mode (`'metric:criticality'`, worst-of over a capability's supporting systems, `src/ui/capabilityMap/metrics.ts`) and a landscape one (per-system, no rollup needed). `hostingModel` is a **closed, unordered** set with no "worst" value to aggregate to, so it is landscape-only (`src/ui/landscape/landscapeColour.ts`) and never offered as a capability-map mode.

The landscape gains its first colour-by mechanism at all this sprint (`LandscapeCanvas.tsx` previously drew every tile with one flat neutral fill, varying only for diff state) — a new sibling preference column, `user_preferences.landscape_colour_by` (migration `20260911080000_landscape_colour_by.sql`, which also widens `capability_map_colour_by`'s check constraint to admit `'metric:criticality'`), a `ChipTone`→`--status-*` tint applied only in the canvas's plain (no active diff) fill branch — never mixed with a diff-state tint, per UI-principles §8.4's "status and diff must not be read across" — and the colour-by's own value surfaced as text in the existing hover tooltip (§8.7: status is never colour-only).

Two new Health findings (`src/db/healthFindings.ts`): "critical systems with no business owner" (`findCriticalSystemsWithoutBusinessOwner`, depending on item 2's `owns.role` data already having landed) and "critical systems exposed with no planned replacement" (`findCriticalExposedSystems`, a system-level analogue of `metrics.ts`'s own capability-level `lifecycleExposure` — same documented "no planned replacement" simplification: nothing today can record one, so that half of the condition is vacuously true until UI-principles §10 decision 4's review-queue machinery exists).

**Amended (Prompt 7k item 3, IT/OT domain).** `SystemAttributes` gains one optional field, TS-contract-only like item 1's own three: `domain: 'it' | 'ot' | 'hybrid'`. Absent reads as `'it'` — the prompt's own stated default, and the only attribute in this whole sprint given a *read-time* default rather than staying silent when unset (`src/ui/elements/systemDomain.ts`'s `domainOf`) — never written back onto a system that never recorded one. `ContainerAttributes`/`ComponentAttributes` gain no `domain` field of their own: a Container/Component's domain is resolved by walking `parent_id` up to the nearest System (`resolveElementDomain`, bounded at four hops by the taxonomy's own fixed depth), so there is no second copy of the fact that could drift out of sync with the System's own.

The landscape's OT zone (`src/ui/landscape/layout.ts`'s `OT_ZONE_LANE_KEY`) is structurally analogous to the existing External lane (`placementFor` pulls a `domain: 'ot'` system out of its normal capability-lane placement the same way `isExternal` already does, checked second, after external) but placed *inside* the enterprise boundary rather than outside it, ordered after capability lanes and before Unassigned (a judgment call, recorded here: real domain-based grouping reads more like "another lane" than a leftover bucket) — `LandscapeCanvas.tsx` also draws a second, smaller dashed rectangle around just that lane's own y-range as the "labelled zone" visual cue the prompt asks for. `domain: 'hybrid'` deliberately stays in its normal capability lane, not zoned out — only a system whose domain resolves fully to `'ot'` is pulled out. An external OT system lands in the external band, not the OT zone: the external check runs first, since "outside the boundary at all" is the more fundamental fact of the two.

Two new colour-by modes, following item 1's own naming convention (`metric:X`) rather than the shorthand `'it-ot'` name floated when this sprint was planned, for consistency with `metric:criticality`/`metric:hostingModel`: the landscape's `metric:domain` (`landscapeColour.ts` — never silent, unlike criticality/hosting, since `domainOf`'s own read-time default means every tile always has a tone) and the capability map's `metric:otShare` (`metrics.ts`'s `otShareOf` — a *fraction* of a capability's supporting systems whose domain is `ot`, summed rather than worst-of'd across an L1 group, and silent at zero since "no OT systems" is the ordinary case for most capabilities in a regulated estate). Both required widening the `user_preferences` colour-by check constraints again (migration `20260911090000_it_ot_colour_by.sql`, same drop-and-recreate shape `20260911080000` already used).

The "Boundary crossings" list (`/o/:org/m/:model/boundary-crossings`, `BoundaryCrossingsPage.tsx`, reachable from a count-and-link block on the architect door mirroring the existing Review-queue block) and this item's own Health finding ("a crossing with no data classification or verb") share one crossing-detection pass, `src/db/healthFindings.ts`'s `findBoundaryCrossings`: every `uses`/`flows_to` edge whose two endpoints resolve to opposite sides of the IT/OT boundary. A `'hybrid'` endpoint never participates in a crossing on either side — ambiguous by construction, a judgment call recorded here. The health finding (`findBoundaryCrossingsMissingClassificationOrVerb`) filters that same list to crossings missing a verb-phrase label or (for `flows_to` only — `uses` has no `dataClassification` attribute to be missing) a data classification; item 5's own narrower "boundary crossings without data classification" Assurance finding (`findBoundaryCrossingsMissingClassification`, below) reuses this same `findBoundaryCrossings` list rather than re-deriving crossing detection a second time.

**Amended (Prompt 7k item 4, integration platforms).** `SystemAttributes` gains `kind: 'application' | 'integration_platform' | 'data_platform' | 'infrastructure'`, another read-time default (absent reads as `'application'`, `src/ui/elements/systemKind.ts`'s `kindOf` — the same pattern item 3's `domain` already established, not a second one invented). `UsesAttributes`/`FlowsToAttributes` each gain an optional `via: UUID` — an element ref to the `system` (of `kind: 'integration_platform'`) the flow actually goes via, not a third real endpoint of the relationship itself. A new commit invariant, **C18**, validates `via` at `relationship.create`/`relationship.update` (`src/engine/deltas.ts`'s `checkVia`): the referenced element must exist in the head as it stands when the delta is applied and be a system with `kind === 'integration_platform'` — not re-checked at `relationship.restore`, deliberately mirroring C9's own endpoint check, which restore also never re-runs (a restored edge is trusted to reconstruct exactly the state it last held).

`RelationshipAdd.tsx` gains a genuine third staged prompt for `uses`/`flows_to` (after the mandatory verb-phrase label Sprint U4-1 B5 already requires): "does this go via an integration platform?", a second search-first picker scoped to `kind: 'integration_platform'` systems, with a prominent "Skip — direct edge" default. This needed a real stage discriminator (`showViaStage`) rather than a second boolean branch, since the existing `asksPrimary`/`needsLabel`/`asksOwnsRole` shape was one boolean each, never two stages deep for the same relationship type. `useRelationshipTargetSearch` gained an `enabled` flag so the second (platform) search instance only ever fetches for `uses`/`flows_to` slots, not for every other relationship-type "+ Add" control on the same element page.

The landscape's platform band (`layout.ts`'s `PLATFORM_BAND_KEY`) is structurally the same shape as item 3's OT zone — a non-`'application'`-kind system is pulled out of capability-lane placement before any `supports` edge is considered — but ordered last of all (after the OT zone and even Unassigned: "along the bottom" read literally, a judgment call recorded here since the prompt names no explicit order among the three zones). Priority when a system qualifies for more than one zone: external, then OT, then the platform band, then an ordinary capability lane — each check is more specific than the next, and a system keeps whichever most-specific placement applies rather than the checks being re-litigated against each other. The "route via platforms" toggle (`LandscapePage.tsx`, plain unpersisted `useState`, never a stored preference — direct edges by default, per the prompt's own parenthetical) draws an edge carrying `via` as two independently-routed legs (from→platform, platform→to) instead of one when on; `layout.ts`'s `viaPositionFor` is the pure decision extracted so it's unit-testable without a canvas.

"Flows via this platform" (the platform element page section) reads a new `flowsViaElement`/`listFlowsViaElement` query — commit-scoped like every other bulk read here (CLAUDE.md rule 8), filtered to `via` client-side rather than pushing a raw jsonb operator into postgrest, since `attributes ->> 'via'` has no existing precedent to extend. Only ever fetched for a system with `kind: 'integration_platform'` (`useElementPage.ts`'s own gate), so every other element type pays nothing for it. The health finding ("an integration platform with nothing flowing via it", `findUnusedIntegrationPlatforms`) reuses the same commit-scoped `uses`/`flows_to` edge list `findBoundaryCrossings`/`findUnlabeledVerbRelationships` already read, rather than a third query over the same rows.

Docs-only: `docs/SPEC-capture.md`'s column-synonym table gains `hostingModel`/`hostingProvider` (item 1), `technicalOwner` (item 2, parallel to `owner`), and `integrationPlatform` (this item, mapping to `via` on a row's own `usesSystems`/`flowsTo` proposals) — plus Prompt A's field list and role meanings. Found and fixed while touching that table: it still described `owns` proposals as defaulting to `primary: false`/a primary-style promotion scheme, stale since item 2's `role` migration; corrected to "role comes directly from which header matched" (`owner` → `business`, `technicalOwner` → `technical`), never a rank-based default.

**Amended (Prompt 7k item 5, regulatory alignment).** Two more optional, TS-contract-only fields, same "no migration for an attribute-only addition" shape as items 1/3/4: `CapabilityAttributes.essentialFunction: boolean` (NIS/CAF's "essential function," recorded at capability level — a regulator asks which *capabilities* are essential, not which systems — and derived down to supporting systems through `supports`, never stored redundantly on a system) and `SystemAttributes.supportEndsAt: ISODate` (vendor support end, deliberately distinct from `plannedEnd`: this estate's own planned decommission date and a vendor's support horizon are two different facts that can each be well past or well ahead of the other).

Three new Health findings (`src/db/healthFindings.ts`), grouped under a new "Assurance" panel on the architect door (its own zero-gate, separate from the existing Health findings panel's): "systems supporting an essential function with no technical owner" (`findSystemsSupportingEssentialFunctionWithoutTechnicalOwner`, depending on item 2's `owns.role` data), "boundary crossings with no data classification" (`findBoundaryCrossingsMissingClassification`, the CAF A3/B4-relevant subset of item 3's own wider crossing finding, reusing the same `findBoundaryCrossings` pass rather than a second detection), and "critical systems past or within 12 months of vendor support end" (`findCriticalSystemsPastOrNearSupportEnd`, a `supportEndsAt`-keyed sibling of item 1's own `findCriticalExposedSystems`, which reads `plannedEnd` instead).

**Explicit out-of-scope guardrail, recorded so a later sprint doesn't quietly build either under the assumption it was simply missed:** a security zone on containers and a dedicated compliance view are both out of scope for this decision. The ordinary model — capabilities, systems, `supports`/`uses`/`flows_to`, the domain/criticality/essential-function attributes above — answers CAF A3/A4/B4 and IEC 62443 zone/conduit questions as ordinary views (the Assurance panel, the Boundary crossings list, the browse table's own filters) rather than needing a purpose-built compliance screen or a new zone concept layered onto containers. Separately, `docs/UI-principles.md` carries a note that the Cyber Security and Resilience Bill's final scope should be verified before any marketing claim referencing it — a legal/product fact, not an engineering one, so it lives there rather than here.

**Amended (Prompt 7k, "Retire…"/"Remove from model…", the changes-discussion item shared across 7k).** Two element-header actions, gated identically to `Edit` (`canEditBranch`: owner/architect at `main`, or owner/architect/contributor on a draft change branch) — "both respect the selected ref" is that existing gate, not a new one.

"Remove from model…" (`useElementRemoveFromModel.ts`, every element type) generalises the old `useElementRetract.ts`/`CapabilityRetractAction.tsx` (Sprint U4-1, capability-only, and only ever usable on a leaf with zero relationships) into a real cascade: one commit containing an `element.retract` plus a `relationship.retract` for every live relationship touching the element — C8's relationship half ("every relationship with the element as an endpoint... is retracted... in the same commit"). It deliberately does **not** attempt C8's other half (re-parenting or retracting a retracted element's own children) — that remains a real, open engine gap, not silently claimed here — so the menu item is omitted entirely (not shown disabled, the same convention `ElementHeader.tsx` already uses for every other optional action) whenever the element has any live children. The old two files are deleted outright, not kept alongside the new hook: neither had any other caller.

"Retire…" (`useElementRetire.ts`, system only — `lifecycleStatus` is not a field any other element type's attributes carry) sets `lifecycleStatus: 'retiring'` and a required `plannedEnd` via the same `element.update` shape `useElementEditor.ts` already uses, plus an optional "replaced by" picker. Choosing a replacement retracts the retiring system's own `supports` edges and creates equivalent ones from the replacement, one capability at a time, in the *same* commit — this is what actually clears a capability's "lifecycle exposure" colour-by (`src/ui/capabilityMap/metrics.ts`'s `lifecycleExposure`, which reads every *live* `supports` edge into a capability; leaving the retiring system's own edge in place would keep it reading exposed regardless of what else supports the capability). New edges always get `role: 'secondary'`, never a copy of the original edge's role, and the replacement's own existing edges are not pre-checked for a duplicate before commit — both are deliberate simplifications recorded here: promoting a role could collide with a `primary` edge elsewhere on the replacement (C17), and checking for either case correctly on a change branch would need the branch-projection read path `useElementPage.ts`'s own module comment already documents as a real gap for a client-side read outside that hook. C10 (no duplicate live relationship) and C17 are both enforced at the commit boundary regardless, so a genuine conflict rejects the whole commit with a real message rather than silently doing the wrong thing.

**Amended ("Platforms and modules").** `SystemKind` gains a fifth value, `'platform'` (Salesforce, SAP, Dynamics: a large, extensible platform whose own `Container` children are its modules). This is a new *meaning* layered onto the existing structural relationship (`parent_id`/`parentId`), not a new relationship type or a schema change to containment itself — a platform's modules were always reachable as its children; what's new is that a module now `supports` a capability directly, not the platform. `relationshipTypeRules.ts` gains one row, `(supports, container, capability)`, mirroring the existing `(supports, system, capability)` row's own `maxPrimaryPerFrom: 1` — legal for any container, not gated to "only a platform's own module" (this table has never expressed anything finer than `(relationshipType, fromType, toType)`). No migration: C17 (`checkPrimaryCardinality`) is already generic on the anchor element's id with no type check, and the existing partial unique index (`relationships_head_one_primary_supports_per_system`, keyed on `(commit_id, from_element_id)` with no type restriction) already backstops a container anchor too.

`ContainerAttributes` gains five new optional fields — `lifecycleStatus`, `criticality`, `hostingModel`, `hostingProvider`, `domain` — **superseding item 3's own amendment above**, which said "`ContainerAttributes`/`ComponentAttributes` gain no `domain` field of their own": that was true until this feature, and remains true for `ComponentAttributes` and for every field except these five on `ContainerAttributes`. A module's own value for each, when set, overrides its platform's; when absent, it *effectively* reads as the platform's own value instead (`src/ui/elements/moduleAttributes.ts`'s `effectiveModuleAttributes` — an explicit five-field allow-list, never a blind spread of the platform's attributes onto the module's, which would leak `kind: 'platform'` onto the module and corrupt `kindOf`/`isNonApplicationKind`/`isPlatform` wherever later called on it). Consumed only by capability-map coverage/exposure metrics and the module's own element-page display — landscape zoning (the OT zone, the platform band) reads a module's own uninherited attributes only, so an OT-domain platform never silently pulls its own modules into the OT zone too. `resolveElementDomain` (`src/ui/elements/systemDomain.ts`, item 3's own boundary-crossing resolver) is updated the same way, for a different consumer: it now checks a Container's own `domain` before walking to its parent System, fully backward-compatible for every container that never sets one.

"Retire…" (above) **is no longer system-only**: `useElementRetire.ts` now reads `element.element_type` generically rather than hardcoding `'system'`, so a module (Container) can be retired with a planned end and an optional replacement module the same way a system can — matching "Remove from model…"'s own already-generic scope, not narrowly gated to "only a platform's own module" (any container now carries `lifecycleStatus`/`plannedEnd`, so there's no strong reason to forbid retiring an ordinary one). The landscape places a platform's own modules as their own tiles, one per capability lane, labelled `` `${platform.name} · ${module.name}` `` (e.g. "SAP · PM") — reusing the existing lane-placement/layout machinery entirely unmodified (`layout.ts`'s `placementFor`/`groupSystemsByLane` are already generic over `ElementsHeadRow`, keyed by `from_element_id`; a module has no `kind` of its own, so it never falls into the platform band the way the platform itself does) — while the platform's own tile still lands in the platform band, exactly as any other non-`application`-kind system does. The platform's own element page gains a "Modules" section (grouped by capability, mirroring `RelationshipsSection.tsx`'s own labelled-group shape) and a "+ Add module" control (`ElementSearchAdd elementType="container" parentId={platform.element_id}`, mirroring `ContainerPage.tsx`'s existing usage of the same control).

**Amended ("V2 — landscape focus and filters").** Three more nullable preference columns on `user_preferences` (migration `20260913090000_landscape_lane_display.sql`): `landscape_collapsed_lane_keys text[]`, `landscape_expanded_lane_keys text[]`, `landscape_pinned_lane_keys text[]` — no new data-model concept, the same "person-scoped, not org-scoped" table this ADR's own decision 1 (UI-principles §10) already establishes and `landscape_colour_by`/`capability_map_colour_by` (above) already extend one column at a time. Two directional override arrays rather than one signed set, because a user can override *either* the empty-lane→collapsed or the non-empty-lane→expanded default, in either direction — `landscape_pinned_lane_keys`' own array order *is* the pin display order, read/written by `useLandscapeLaneDisplayPreference.ts` exactly as `landscape_colour_by` already is by its own hook. Filters (`?capabilities=`/`?lifecycle=`/`?criticality=`/`?kind=`/`?domain=`) are deliberately **not** a preference at all — they live in the URL (`landscapeFilterParams.ts`), so a filtered view is a paste-able link (§2.4's "any element, at any level, in any version, has a URL"), never a silent per-user default that would make the same link show different systems to different people. Neither mechanism touches `elements_head`/`relationships_head`/`deltas` in any way — both are pure read-side lenses over the already-materialised head, same as every other view-only preference this table holds.

**Amended (S1 item 11a, external actors).** `ActorSubtype` gains a third value, `'organisation'` (a regulator, a supplier — an external third-party entity, as distinct from an internal `person`/`team`), alongside `isExternal`/`externalOrganisation`, both already present on Actor since this decision's original text (§35/§53 above) — this item's actual new ground is everything below, not those two fields.

`relationship_type_rules` gains two rows: `(uses, actor, system)` and `(uses, actor, container)` — "Ofgem uses the reporting system" is a real, drawable `uses` edge now, not confined to the page-only `owns` relationship the original decision (§18-24 above, restated in `contextGrouping.ts`'s own module comment) said was the *only* way an actor could ever reach a system. `owns` is unaffected and remains the accountability relationship; `uses` is the access one. No cardinality cap, same as every other `uses` row. `flows_to` still has no actor-endpoint row at all — a flow is a System/Container-to-System/Container fact, unchanged; an external actor's own access is expressed as `uses`, never as a flow.

A new commit invariant, **C20** (`src/engine/deltas.ts`'s `checkExternalOwnerRole`), constrains the `owns` relationship this item does *not* otherwise touch: an `owns` edge whose owning actor is external (`isExternal === true`) must set `role: 'service'` — an external actor never holds `business`/`technical` accountability inside the enterprise, only a service relationship to it. Checked at `relationship.create`/`relationship.update`, not re-checked at `relationship.restore`, the same convention C18 already established for its own cross-entity check. No database backstop, also matching C18's own precedent: this is a cross-table (relationship attribute ↔ the owning element's own attribute) dependency Postgres has no plain `CHECK`/index for, and C18 already established that engine-only enforcement is this taxonomy's accepted answer for that shape of rule.

The landscape and Context view both render an external actor the same way they already render an external system — "outside the enterprise boundary" is one shared visual rule keyed on the same `isExternal` attribute regardless of element type, not a second rule invented for actors:
- **Landscape** (`layout.ts`): an internal actor keeps the pre-existing top-row placement, above the boundary; an external actor instead joins the External band below the boundary, alongside external systems — one "outside" region for everything external, not a second region just for actors. A `uses` edge into or out of an actor draws on the canvas exactly like a system-to-system edge (the routing/arrowhead code was already generic over node position, `layout.ts`'s `LandscapeNodePosition` is shared by system and actor nodes alike — the gap was purely two places that filtered the actor id out of the edge/endpoint sets before this item, both widened), plus a new on-canvas verb-phrase label at the edge's own midpoint (scoped to actor-involved edges only — a system-to-system `uses`/`flows_to` edge still has no on-canvas label, unchanged; its own verb phrase has only ever shown on the element page and the Context view).
- **Context view** (`contextGrouping.ts`): a `uses` edge from/to an actor now flows through the same `internal`/`external` neighbour classification a system neighbour already used — no special-casing needed there once the relationship-type rule made the edge legal at all. `owns`, which still has no drawn edge (§18-24 above is otherwise unchanged), gets its own internal/external split instead: `ContextOwner` gains `isExternal`/`externalOrganisation`, and the "Owned by" summary line splits an external service owner into its own trailing "External: <organisation>" clause rather than folding it into the same "Service owner:" list an internal one would appear in.

Two new Assurance findings (`src/db/healthFindings.ts`), grouped under the existing "Assurance" panel (item 5 above) alongside its original three — five checks there now, not three:
- **"External interfaces missing a data classification"** (`findExternalInterfacesMissingClassification`) — a sibling to item 3's own IT/OT `findBoundaryCrossings`, keyed on the enterprise/external boundary (`isExternal`/a named `externalOrganisation`) instead of the IT/OT domain boundary; the two boundaries are independent facts about an edge and can cross one, both, or neither. Scoped to `flows_to` only, for the same "`uses` has no `dataClassification` attribute to be missing" reason item 3's own finding already gives; an actor is never counted as either side here — a `flows_to` edge can't have one at all, and an actor's own access is a different fact, the finding below.
- **"External organisations with access"** (`findExternalOrganisationAccess`) — purely informational, not a metadata gap: every external actor's own `uses` edge, naming the organisation and which system it reaches. One row per edge, not deduplicated by organisation.

Both findings' own "View all →" link opens one new page, `/o/:org/m/:model/external-interfaces` (`ExternalInterfacesPage.tsx`/`ExternalInterfacesView.tsx`, mirroring `BoundaryCrossingsPage.tsx`'s own shape) with two independent sections — a model can have a classification gap with nothing external having access at all, or vice versa.

**Amended (S1 item 18, remove the component level).** *Element types (four, not five): Capability, System, Container, Actor.* Component is removed from the taxonomy entirely — the zoom chain becomes capability → landscape → system context → containers (UI-principles §2.1's own "five levels" becomes four), and Container is now its last stop. This was a genuinely unused fourth structural layer: nothing in this product's own review found a case for modelling one level below Container that Container itself couldn't already carry (a container that's too coarse-grained is a case for a second, sibling Container, not a fourth taxonomy level).

`ComponentAttributes` is deleted from the contract (`src/contracts/delta.ts`) rather than deprecated in place — unlike the `owns.primary`/`role` amendment above, there is no live data migration this decision has to stay compatible with: the component route, view, create path, breadcrumb step, and every nav reference to it are removed in the same change (`src/ui/routes/ComponentPage.tsx` deleted; `StructureView`/`useStructureView` collapse from a `kind`-parameterised container/component pair to Container alone). `relationship_type_rules` loses its two component rows (`uses: component→component`, `uses: component→container`).

A new migration (`supabase/migrations/20260913010000_remove_component_element_type.sql`) refuses to apply if any model on the target database still has a live component element (`elements_head`) or a component-scoped view/comment — the fix there is a real `element.retract` delta via a commit, or deleting the offending view/comment through the application, not a hand-edit. The migration deliberately leaves `deltas.element_type` untouched as an enum-typed column — it widens it to `text` instead, since `deltas` is immutable append-only history (rule 5) and a component element created (then retracted) at any point before this migration leaves a real, permanent `element.create` delta recording `element_type = 'component'`, a fact schema evolution must never rewrite or erase. `elements_head`/`views`/`comments` — live, rebuildable-from-`deltas` state with nothing legitimately still pointing at the retired value — get the tightened `element_type`/`view_kind` enums.

**Amended (F1, "custom attributes").** Core attributes stay code (this decision's own attribute-set table above, materialised as `src/contracts/attributeSchema.ts`'s `ATTRIBUTE_SCHEMA_BY_TYPE` pending the `type_schemas` registry SPEC §3.3 defers to Sprint K1); the long tail becomes org-defined data instead. A new table, `attribute_definitions` (SPEC §3.2 — org-scoped, applying across every model in the organisation, never a single model), lets an owner define an attribute (`key`, `label`, `kind: text|number|date|boolean|select|link`, `options` for `select`, `applies_to` — one or more of Capability/System/Container/Actor), reorder it among its siblings, and deprecate it. A custom value lands in the exact same `attributes` jsonb as any core attribute, with the same per-fact provenance (`facts`, ADR-007) — never a second, parallel storage mechanism.

Two new delta kinds, `element.update_custom`/`relationship.update_custom` (SPEC §4.1), are the only writers. Deliberately **not** a widened `element.update`/`relationship.update`: `ElementUpdate<T>`'s own `attribute` field is a distributive conditional type keyed by a closed literal union of every core attribute key for `T` — the whole point being that a typo'd or removed core key fails to compile, not silently no-ops. Widening it to accept an arbitrary org-defined string would lose that guarantee for *every* element update, core included. The two new kinds also never special-case a custom key that happens to be spelled `name`/`parentId` (or, on the relationship side, `role`/`via`) the way the real promoted-column/cardinality logic does — a custom key always writes straight into the `attributes` jsonb, with no risk of being mistaken for one of those.

No new engine-level (fold-time) validation exists for a custom attribute's value — a deliberate choice to match, not exceed, the bar core attributes are already held to: reading `src/engine/deltas.ts`'s `apply()` in full shows it validates exactly five things inline (C8/C9/C17/C18/C20); everything else, core attribute values included, is assumed already checked before the commit reaches it. `atlas.commit_deltas` writes the `attributes` jsonb verbatim regardless of kind, core or custom. Validation for both lives in exactly one place, client-side, at the commit boundary (`src/contracts/attributeSchema.ts`'s `validateAttributeValue`/new `validateCustomAttributeValue`, both now delegating to a shared `validateByKind`), before a delta is ever built — building real server-side validation for custom attributes only would make them *more* trustworthy than core attributes are today, solving a problem nothing asked this sprint to solve.

`AttributeKind` gains two members this taxonomy didn't have before, `number` and `link` (`AttributeValueInput.tsx` gets matching `<input type="number">`/`<input type="url">` branches) — F1's own six wire kinds are `text|number|date|boolean|select|link`; `select` is this codebase's existing `enum` kind under a different name in the prompt's own prose, not a fourth thing invented, and `attribute_definitions.kind = 'select'` maps to `AttributeKind.enum` at the one boundary that matters (`attributeDefinitionToFieldSchema`) rather than renaming `enum` everywhere it's already used by every core field.

Rendering and editing reuse `AttributeRow`/`AttributeEditRow`/`AttributeValueInput` completely unmodified — `attributeDefinitionToFieldSchema` maps a definition onto the same `AttributeFieldSchema` shape every core field already uses, so nothing downstream needs to know a field is custom rather than core. A deprecated definition disappears from the edit form's own field list outright (mirroring `models.archived_at`'s "hide forward choice, never data"), but keeps rendering read-only, unchanged, for any element that already has a value under it.

The browse table's own filter/sort (`src/ui/elements/useElementBrowse.ts`, `ElementBrowseTable.tsx` — not otherwise documented outside application code) widens with one generic facet, not one hardcoded variant per attribute: `ElementBrowseFilter` gains `{ custom, value }` (an equality filter, `value` already parsed to the definition's own kind before it reaches the filter) and `ElementBrowseSortKey` gains `{ custom }` (a generic ordering — numeric compare for two numbers, false-before-true for two booleans, `localeCompare` otherwise, which already orders an ISO date string correctly with no per-kind branching needed).

Promotion to core (the prompt's own "code change + data-migration commit") is a documented process, not an in-app feature — nothing in the product automates it. **Explicitly out of scope, recorded so a later sprint doesn't quietly build it under the assumption it was simply missed:** no colour-by mode, no Health/Assurance finding, and no engine rule of any kind reads a custom attribute — those are core-attribute mechanisms (items 1/3/4/5 above), deliberately not extended to org-defined data this sprint.

**Amended ("replaces" relationship type, `20260921030000_relationship_type_replaces.sql`).** A fifth relationship type — *supports, uses, owns, flows-to, and now* **replaces** — recording that one system or module replaces another, directionally: `fromElementId` is the replacement, `toElementId` is the retiring element ("B replaces A" is `from: B, to: A`). This closes a real gap the Roadmap had been papering over since F5: its own "replace" arrow was never backed by a stored fact, only a same-change heuristic (a `supports`-edge retract paired with a create into the same capability) — coincidental, not causal, and blind to any replacement recorded outside that one narrow shape. `relationship_type_rules` gains four rows, `(replaces, system, system)`/`(replaces, system, container)`/`(replaces, container, system)`/`(replaces, container, container)` — the same promiscuous system/container reach `uses`/`flows_to` already have, and, like those two, **no cardinality cap in either direction**: a `replaces` edge is an ordinary many-to-many fact, not a primary/secondary-capped one like `supports`/`owns`. This is the shape that makes both of the following render correctly with zero special-casing, and both are exercised directly by tests, not just asserted:

- **Consolidation** — two retiring elements sharing one replacement — is two `replaces` edges with the same `from_element_id`, different `to_element_id`.
- **Split** — one retiring element with two replacements — is two `replaces` edges with the same `to_element_id`, different `from_element_id`.

**Explicitly not a data migration.** A repo-wide search before this amendment confirmed there is no existing stored `replacedBy` attribute or relationship anywhere in this schema to convert. The only prior art was always transient and never persisted: the JSON import's `changes.replacedBy` column and the "Retire…" action's own "replaced by" picker both, before this amendment, only ever *transferred* the retiring element's own `supports` edges to the replacement (`role: 'secondary'`) — the replacement reference itself was discarded the moment the commit was built. `replaces` is new schema recording a fact that was never recorded before, not a conversion of one that was.

`ReplacesAttributes` (`src/contracts/delta.ts`) carries only an optional free-text `description` — no `role` (nothing here caps at one primary per anchor), no `via` (a replacement is a fact, not a routed flow). `src/engine/mergeElements.ts` needed no production change at all: its relationship retract/self-loop-drop/duplicate-drop/repoint logic is already generic over relationship type, and because `replaces` has no cardinality cap, the one type-specific branch in that file (the `supports`/`owns` primary-collision special case) is never reached for it — proven by a regression test, not left to inference.

**Amended ("replaces" read path: exposure).** "No planned replacement" — the second half of lifecycle exposure that the earlier simplification note (Prompt 7k item 1) treated as vacuously true because nothing could record one — now reads a real fact: a system (or module) with a live `replaces` edge pointing at it (`to_element_id`, the retiring side; `replacedElementIds` in `src/engine/elementRead/fitAndExposure.ts`) never counts as exposed, however near or past its own `plannedEnd`. It is applied in `systemsExposedByLifecycle`/`lifecycleExposure` (so the capability map's Lifecycle exposure colour-by, its roll-ups and its export) and in `findCriticalExposedSystems` (the Home check, the Elements filter and the model tool). The check is existence-only and the `replacedIds` argument is optional, so a caller that hasn't loaded `replaces` edges keeps the plain `plannedEnd` reading; the Portfolio rows and the decision page's "Trigger resolved" row do not pass it yet. **Considered and dropped:** a "replacement with no departure plan" finding (an active replacement with no `plannedEnd`) was built and removed again — a system that has just taken over normally has no end date, so it flagged every recorded replacement. **Explicitly not handled:** an element that returns to `active` after being replaced keeps its live `replaces` edge, so it stays hidden from exposure until the edge is removed; recording a rule for that is left for when it is needed.

**Amended (F6, value streams — `docs/ADR-023-value-streams.md`).** *Element types (five): Capability, System, Container, Actor, Value stream.* *Relationship types (six): supports, uses, owns, flows-to, replaces (the amendment directly above), enables.* A value stream is a `value_stream` element with no parent; its stages are child `value_stream` elements (depth exactly two, C22), ordered by the same `order` attribute capabilities already use; `enables` is capability → stage only ("this capability is one of those that deliver this stage"), with no attributes and no cardinality cap. This is the "one business layer" this decision said the taxonomy had to carry, widened by one grouping above capability — and it is **not** the "business processes/workflow steps (BPMN-shaped)" non-type above: a stage is a label grouping the capabilities that deliver it, with no sequence semantics beyond display order, no timing, no per-stage owner (`owns`/`uses`/`flows_to` gain no `value_stream` row) and nothing modelled between two stages. `DELIBERATELY_NOT_MODELLED` keeps `business-process`. A stream is deactivated (three attributes: `inactive`, `inactiveSince`, `inactiveReason`), never retracted — `Remove from model…`/`Retire…` are omitted for the type — and its structure (streams, stages, `enables` edges alike) is editable on `main` or in a `correct`-intent change only, a UI-level gate ADR-023 states in full. Adding the type costs exactly what the Consequences paragraph above says it should: a migration widening two enums, contract types, one rules row, one engine invariant, and every exhaustive map in the codebase.

## ADR-002: Delta representation, commits, branches, and tags

**Context.** Changes have to be branchable deltas against the current landscape, mergeable through review, and every change has to carry its own provenance. The representation has to support git-shaped vocabulary (branch, commit, tag) without inheriting git's blob/tree model, which isn't built for typed, queryable, tenant-scoped facts.

**Decision.** A **delta** is one fact assertion, not a generic patch operation. `deltas`: `id`, `origin_commit_id` (the commit that introduced it — immutable, for blame/history), `subject_type` (`element`/`relationship`), `subject_id`, `operation` (`create`/`update`/`retract`), `attribute` (nullable — unset for whole-object create/retract), `value` (jsonb), `previous_delta_id` (nullable — the fact this one supersedes, same subject+attribute), `source`, `source_ref` (pointer into the originating document, e.g. sheet/cell or PDF page), `effective_date`, `confidence`, `created_by`.

A **commit** groups a batch of deltas: `commits`: `id`, `branch_id`, `parent_commit_id`, `merged_branch_head_commit_id` (nullable — set only on merge-kind commits; this makes commit ancestry a DAG with two parents on a merge, exactly like a git merge commit), `kind` (`manual`/`capture`/`merge`/`template_seed`), `author`, `message`, `created_at`.

*(Sprint U4-1 amendment.)* `message` is `title` (renamed) plus `body` (added). `title` is no longer caller-typed: for a `manual` commit it's generated from the commit's own deltas (`src/engine/describeEnvelope.ts`) — real element and relationship names, not a hand-written summary. `body` is an optional caller elaboration nothing writes a real one into yet. See SPEC-data-model.md §5.1 for the full detail.

A **branch** is a named, mutable pointer: `branches`: `id`, `org_id`, `model_id`, `name`, `kind` (`main`/`change`/`capture_draft`), `base_commit_id`, `head_commit_id`, `status` (`draft`/`proposed`/`in_review`/`approved`/`merged`/`rejected`/`archived`), `created_by`.

A **tag** is an immutable, never-moved pointer, and is how "version" is implemented: `tags`: `id`, `org_id`, `model_id`, `name`, `commit_id` (must resolve to a commit on `main`), `created_by`, `created_at`. A tag row is insert-only — there is no update or delete path — and it does **not** duplicate the landscape's state; it points at a commit, and the materialised state at that commit is computed as described in ADR-003.

Because a merge commit has two parents, a delta authored on a change branch and "the same delta as it appears on main after merge" are the identical row — main's ancestry simply now includes it. No delta is ever copied or rewritten to migrate it from branch to main.

**Alternatives rejected.**
- *JSON Patch (RFC 6902) as the persisted format* — patch operations are path-context-free; they can't carry per-fact provenance/confidence without an ad-hoc wrapper, and "show every fact ever recorded about System X" requires replaying every op rather than a plain query. Diff-style JSON Patch is fine as a *transient, computed* representation for a UI diff view, never as storage.
- *A single mutable "current state" table with an audit log bolted on* — makes deltas second-class, and branches (which are the product's actual wedge) become awkward to represent as first-class diffable objects.
- *Literal git storage* (real git blobs/trees under the hood) — optimised for text files, not typed relational facts; cross-branch, cross-tenant queries and RLS (ADR-009) are native to Postgres and not to git. The vocabulary is deliberately git-shaped; the persistence is not.

**Consequences.** History is append-only — nothing is ever hard-deleted, which is a strength for audit but means storage grows monotonically forever; a retention/compaction policy is a real future need but is explicitly out of scope here (flagged, not designed).

## ADR-003: Materialised head — rebuild and validation

**Context.** "Main" has to always be a valid landscape — every other branch forks from it, and every view renders from it. Replaying the entire delta history from genesis on every read doesn't scale once a landscape has thousands of deltas.

**Decision.** Maintain a materialised projection — `landscape_elements`, `landscape_relationships` — but only persist it as a cache at commits that matter: the current head of `main`, and the head of every open branch. A snapshot is taken automatically whenever a tag is created and whenever `main`'s head advances, so replaying any historical or arbitrary commit only has to walk deltas back to the nearest prior snapshot, never to genesis.

Before a commit can become the new `main` head (i.e. as the last step of a merge, ADR-006), it must pass a validation gate:
1. **Schema validation** — every element's attributes satisfy the active `type_schemas` entry for its type.
2. **Referential integrity** — every relationship's endpoints and every structural `parent_*_id` reference an existing, non-retired, correctly-typed element.
3. **Relationship rules** — every relationship's (type, source type, target type) triple exists in `relationship_type_rules`, and cardinality limits hold.
4. **Acyclicity** — no cycles in any `parent_*_id` chain.
5. **Identity integrity** — no retracted/merged-away id reappears as if live (checked against the `merges` table, ADR-008).

A commit that fails is blocked from merging and stays on its own branch with the failing checks surfaced to its author. `main`'s head is therefore guaranteed valid at all times — validation is a merge gate, never a background cleanup job.

**Alternatives rejected.**
- *Validate only at read time, best-effort* — `main` is the shared source of truth every other branch and view depends on; letting it go invalid even briefly propagates the problem everywhere.
- *Full graph re-validation on every single delta write* — too slow for interactive review, where a person is toggling many proposed deltas before submitting.

**Consequences.** Merging has real latency (replay + validate), so it is a reviewed, slightly-asynchronous action rather than an instant flip — which fits naturally with the review queue in ADR-006. The rebuild function must be pure and deterministic (same deltas in, same materialised state out) so the review queue's "preview" step and the actual merge step can share one implementation.

## ADR-004: Capture pipeline lands as draft branches

**Context.** Spreadsheets, PDFs, and text need to produce proposed deltas without either forcing a human to pre-decide "which change is this for," or letting AI-produced facts touch `main` unreviewed.

**Decision.** Every capture run creates a branch of kind `capture_draft` (`base_commit_id` = `main`'s head at run time), containing one `capture`-kind commit whose deltas all carry `source` = the ingestion job id, `source_ref` = the document/page/cell locator, and a `confidence` score. `capture_jobs`: `id`, `org_id`, `model_id`, `input_type` (`spreadsheet`/`pdf`/`text`), `input_ref`, `status` (`pending`/`parsed`/`reviewed`/`discarded`), `resulting_branch_id`, `created_by`.

A `capture_draft` branch is never merge-eligible directly. A human triages it: discard individual deltas, promote accepted ones into a change branch (new or existing — this creates new deltas whose source references the human review as corroboration, without overwriting the original capture provenance, per ADR-007), or discard the whole branch.

**Alternatives rejected.**
- *Write capture output straight into a change branch chosen up front* — forces the user to name "which change" before they've seen what was extracted, when a capture run is often change-agnostic (e.g. "digitise this old spreadsheet").
- *Write capture output straight to main behind a "needs review" flag* — reintroduces an invalid/unreviewed `main`, which ADR-003 exists specifically to rule out.

**Consequences.** The review queue (ADR-006) has two distinct kinds of inbound work — architect-proposed change branches, reviewed as a whole design, and capture-pipeline drafts, reviewed delta-by-delta — and the UI needs to treat them differently rather than as one generic "pending branch" list.

## ADR-005: To-be composition

**Context.** A change branch's to-be view is straightforward (base landscape folded with the branch's own deltas). "All approved branches composed together" is a materially harder problem the brief correctly defers, but the schema shouldn't need to change when it's tackled.

**Decision.** V1 ships single-branch to-be only: a branch's as-is view is the materialised state at its `base_commit_id`; its to-be view is that state folded with its own deltas. No schema work is needed later to support multi-branch composition, because composition is a read-time query over existing `deltas`/`branches` rows, not a new storage shape.

When multi-branch composition is built, **conflict** is defined as one of three classes, distinguished because they need different resolutions: (a) **field conflict** — two branches assert different values for the same (`subject_id`, `attribute`) that both diverge from the same shared base value; (b) **structural conflict** — one branch retires or reparents an element that another branch adds a relationship to; (c) **identity conflict** — two branches independently create what later turns out to be the same real-world thing (resolved through ADR-008's merge mechanism after the fact, not at composition time). Composing multiple approved branches is read-only and advisory (a preview, not something that can itself be committed) until conflict-resolution UX and cross-branch identity merging exist.

**Alternatives rejected.**
- *Auto-merge all approved branches nightly into a "consensus to-be"* — silently resolves exactly the kind of disagreement the product exists to surface and record a decision about.
- *Require branches to be sequential/rebased on each other* — defeats the point of letting several in-flight changes exist in parallel, which is the actual reason composition is wanted.

**Consequences.** Product copy should say "this change's to-be view," singular and branch-scoped, and avoid implying a combined future-state view exists until multi-branch composition actually ships.

**Amendment (Sprint C1): `base_commit_id` moves on refresh.** This decision's original phrasing — "a branch's as-is view is the materialised state at its `base_commit_id`" — read as if `base_commit_id` were fixed forever at the branch's original fork point. It isn't: `head(mergeBase(B))` is what actually governs the As-is view (SPEC §7.1's `mergeBase`, UI-principles §6.2), and once refresh/rebase exists (Sprint C1), a branch's fork point and its current merge base are no longer always the same commit. The two are reconciled, not left to diverge: `base_commit_id` is fixed *between* refreshes, not forever — a refresh (ADR-006, SPEC §7.5) moves it to `main`'s head at the moment it succeeds, so `base_commit_id` continues to equal `mergeBase(B)` and folding at it remains a correct, O(1) way to compute As-is, with no DAG walk needed on every read. The original fork point is not lost, but it is not a stored field or a selectable view either — it stays discoverable only via commit ancestry, as the parent of the branch's first own commit. See SPEC §1 S-11 for the matching schema-level statement.

## ADR-006: Merge review queue

**Context.** Delivered changes need to move from a branch into `main` through review, not by direct write.

**Decision.** Requesting a merge creates a row in `merge_requests`: `id`, `branch_id`, `base_commit_id` (captured at request time), `requested_by`, `requested_at`, `status` (`pending`/`changes_requested`/`approved`/`merged`/`rejected`), `reviewed_by`, `reviewed_at`, `review_notes`. Merge is only possible once: the request is `approved`; `base_commit_id` is still an ancestor of `main`'s current head (otherwise the requester must refresh/rebase — see below); and ADR-003's rebuild-and-validate passes on the replayed result. Merging creates a `merge`-kind commit on `main` (parent = `main`'s previous head, `merged_branch_head_commit_id` = the branch's head) — the branch's own deltas are not copied, per ADR-002. The branch then becomes `merged` and read-only, never deleted, so its own as-is/to-be history stays queryable exactly as it looked when reviewed. Only Architect/Owner roles (ADR-009) can move a request to `approved` or `merged`. A request sent back to `changes_requested` (`request_changes`, branch reopened to `draft`) returns to `pending` via `atlas.resubmit_merge_request` (Sprint C1 step 7, `supabase/migrations/20260906162000_resubmit_merge_request.sql`) once the requester has addressed it — an update to the *same* `merge_requests` row (with a refreshed cached classification, SPEC §7.4: "cached at request and at each refresh"), not a second `submit_merge_request` insert, which the partial unique index on `(branch_id)` for an in-flight status would reject anyway.

**Alternatives rejected.**
- *Rewrite the branch's deltas' commit reference in place at merge time* — falsifies the branch's own immutable history, which stakeholders or a linked decision (ADR-013) may already cite.
- *Fast-forward with no merge commit* — loses the explicit "this reviewed change, by whom, on what date, became reality" marker the whole product is meant to preserve.

**Consequences.** "Your branch is behind `main`, please refresh" is a real, expected UX state, not an edge case — the product should show the requester what changed on `main` since they branched, using the two-way (branch vs. main) case of ADR-005's conflict taxonomy, which is simpler than full N-branch composition and should ship in v1 even though general composition doesn't.

**Amendment (Sprint C1): partial delivery is a split branch, not a partial merge commit.** ADR-002's merge-commit model is all-or-nothing — a merge commit's second parent is the whole branch head, so there is no mechanic for merging "some but not all" of a branch's own deltas in one merge commit. Rather than weaken that append-only guarantee, per-element accept/skip in the review queue is defined as follows:

1. Accepting a subset of a branch's elements/relationships in the review queue moves that accepted set into a **new** branch (`kind = 'change'`, `status = 'approved'`, `split_from` = the original branch's id, same target date as the original), which is then merged whole, in the same review action, using the ordinary all-or-nothing merge of ADR-006. The remainder — everything not accepted — stays on the original branch, whose own `status` is unchanged (still `proposed`/`in_review` as appropriate; it is not implicitly closed by a partial acceptance).
2. The split respects dependencies, computed before it is offered for confirmation: accepting a relationship whose endpoint is an unaccepted new element pulls that element into the split too, and the review queue shows this pulled-in closure before the reviewer confirms. Retracting an element that other, unaccepted deltas on the branch still depend on is blocked, with the dependency named as the reason, rather than silently splitting it away.
3. The change page (UI-principles) treats an original branch and every branch it has been split into as **one logical change**, shown as a single item with a "delivered / remaining" breakdown (what has merged via its splits, what is still open on the original branch); the roadmap view does the same — a split is bookkeeping for partial delivery, not a second change for a stakeholder to track.
4. `branches.split_from` (nullable, → `branches.id`) records this lineage; see SPEC §3.4 for the column and §1 for the corresponding decision entry.

**Alternatives rejected (amendment).**
- *A merge commit that cherry-picks a subset of the branch's own deltas* — falsifies the branch's own append-only history (ADR-002) by making its merged form disagree with what it actually contained when reviewed.
- *Two-phase commit that edits the original branch's deltas after acceptance* — deltas are never mutated post-hoc (ADR-002); a split branch is a new set of pointers over the same immutable delta rows, not a rewrite.

**Amendment (Sprint C2b, ADR-021 — `docs/ADR-021-structural-conflict-resolution.md`): how structural conflicts are resolved, and how a merge commit folds.** Two things this ADR's refresh/merge wording assumed turned out not to hold once structural conflicts were built for (issue #76): a resolution recorded in a later commit can never protect an earlier conflicting delta from the replay in SPEC §6.2's `fold`, on either side — and the final merge on `main` is the fold that is hashed. ADR-021 decides (1) a merge commit whose first parent is an ancestor of its second parent folds to the second parent's state (invariant C19; the merge commit itself stays, exactly as this ADR requires — only its fold rule changes), landing on its own before Sprints 7i–7k; and (2) a refresh is "prepare, replay, decide": an optional `preparation`-kind commit (new `commit_kind`, C21 — renumbered from the ADR's original draft, which had called it C18 before finding that id already taken by an unrelated, already-shipped invariant, ADR-021 §2a amendment 3) makes main's replay applicable, then the `merge` commit carries the reviewer's decision deltas and the `resolved_conflicts` rows, written atomically by `atlas.refresh_branch`. The four actions §7.4 names (keep-retraction / keep-element with cascade, duplicate survivor, cardinality primary) have their exact delta sequences in ADR-021 §4.

**Amendment (F3a, multiple reviewers): "approved" is the aggregate of a set of reviewer verdicts, not one reviewer's decision.** The original decision's single `reviewed_by`/`reviewed_at` "only Architect/Owner may approve" is replaced for a `propose`/`explore` change (intent, ADR-000 F0) by a **reviewer set** recorded in a new `review_verdicts` table (one row per `merge_request_id` + `user_id`, a `required` flag, a `verdict` of `approve`/`request_changes`/`abstain`/`pending`, and an optional `comment`):

1. **Derivation.** Reviewers are derived from ownership — the affected systems' business and technical owners and the affected capabilities' business owners, resolved through `ActorAttributes.memberId` (the actor↔member link: an owner is an Actor *element*; a reviewer must be a *member*), plus one architect — and the proposer may add or remove them. An org setting (`organisations.review_min_required_architects`, default 1) is the floor on how many architect-*or-better* members the required set must include. **Amended (20260926010000_owner_counts_as_architect_reviewer.sql):** an org-role `owner` counts toward this floor the same as an `architect` does — every other role gate in the codebase already treats `owner` as architect-or-better (`src/ui/orgs/roleGates.ts`), and the one place this floor checked `role = 'architect'` literally left a solo-owner organisation (no separate architect member at all) unable to ever submit a `propose`/`explore` change for review, with no safe way out (changing a role at all requires `owner`, so self-demoting to `architect` risks losing `owner` access entirely with nobody left to restore it). Every reviewer may be `required` or optional.
2. **Merge gate.** A request is `approved` when every *required* reviewer has voted `approve` and no reviewer has voted `request_changes`. `abstain` never blocks and never satisfies a required seat. Any `request_changes` — required or optional — returns the request to `changes_requested` and its branch to `draft`, exactly as before. `atlas.merge_branch` is unchanged (still gated on `approved`).
3. **Intent sets the weight.** `record`/`correct` changes keep the single-approver path (one owner/architect approval, no `review_verdicts` rows); `propose`/`explore` use the verdict set. `atlas.submit_merge_request` writes the pending set and notifies each reviewer (`review_assigned`, a new `notification_kind`, linking via `notifications.merge_request_id`).
4. **`set_review_verdict`** casts/updates the caller's own verdict and recomputes the gate transactionally; **`set_reviewers`** lets the proposer (or an owner/architect) replace the set while the request is still `pending`, re-validating the architect floor.

The queue and change page show "n of m" approvals with each reviewer's verdict; comments never block a merge (ADR-010), and a verdict is a gate, not a comment.

**Amendment (review reminders, `20261112020000_review_reminders.sql`): reviews have a timeline.** One organisation-wide period, `organisations.review_period_days` (default 5 calendar days, 1–90; set by an owner or architect through `atlas.set_review_period`, because `organisations_update` is owner-only). A review is *overdue* when it is still `pending` (waiting on reviewers — not `changes_requested`, which waits on its author, nor `approved`) and `created_at + period` has passed; the due date is derived (`src/contracts/thresholds.ts`'s `reviewDueDate`/`isReviewOverdue`), never stored, so changing the period re-dates every open review. Overdue reviews carry a "Overdue" chip on the review itself and its queue row, and Home's "Waiting for review" panel links straight to the oldest. The requester, an owner or an architect can send **one** reminder email to the reviewers who have not responded (`send-review-email` in reminder mode; `merge_requests.reminded_at` is claimed before sending so it can never go twice). There is no per-review due date and no automatic send on the due date — both deliberately left out until decided.

**Amendment (stale-data threshold and owner nudges, `20261113040000_stale_threshold_and_nudges.sql`; detail in ADR-025's amendment).** The 12-month staleness threshold is now per organisation (`organisations.stale_after_months`, 1–60, set through `atlas.set_stale_threshold` by an owner or architect). Staleness covers every element type and ignores the `$exists` fact. An owner or architect can email owners the items of theirs that are stale (`send-review-email`, `staleNudge` mode, button-driven like the review reminder); an item with no owner goes to the architects. Opt-out is `user_preferences.email_on_stale_nudge`; one email per person per model per week, claimed in `stale_nudges`.

## ADR-007: Provenance is fact-level

**Context.** Provenance has to answer "where did this specific field's value come from, and how confident are we," not just "where did this element come from" — the brief is explicit that element-level provenance is the wrong grain, and it's right.

**Decision.** Provenance (`source`, `source_ref`, `effective_date`, `confidence`, `created_by`) lives on the `deltas` row (ADR-002), never on the element/relationship row — an element accumulates facts from many sources over time (name from an interview, vendor from a spreadsheet, lifecycle status from a later email), each needing its own trail. The "current" provenance of a field is simply the provenance of its most recent non-retracted delta — always derivable, never duplicated onto the materialised row (which may cache a `source_delta_id` pointer per field for cheap display, but never the provenance fields themselves).

**Supersession** happens by reference, not overwrite: a new delta on the same (`subject_id`, `attribute`) sets `previous_delta_id` back to the fact it replaces; the prior delta is never edited or deleted, so "what did we believe about System X's vendor in March 2024, and from where" stays answerable forever.

**Conflict surfacing:** when two facts about the same (`subject_id`, `attribute`) disagree with no obvious time-ordering (e.g. two capture jobs disagree on the same day, or a capture draft's proposed value disagrees with `main`'s current value), the review/triage UI shows both, with sources and confidences, rather than silently picking one. A human's resolution becomes a new delta with `source` = "human decision," recorded in `resolved_conflicts`: `winning_delta_id`, `discarded_delta_id`, `resolved_by`, `resolved_at`, `rationale`.

**Alternatives rejected.**
- *Element-level provenance (one source/confidence per element)* — hides exactly the kind of per-field disagreement (a stale spreadsheet vendor field vs. an up-to-date interview) the product exists to catch; this is the brief's own stated failure mode of existing tools.
- *Last-write-wins with no conflict surfacing* — silent overwrite is the "decay" pattern named in the brief's thesis.

**Consequences.** Every UI surface that shows an attribute value needs a per-field provenance affordance (source, date, confidence on hover/expand), not one metadata panel per element — a real UI cost, but the core value proposition.

## ADR-008: Identity and merging

**Context.** Capture pipelines will see the same real-world thing under different names across different documents; the product has to converge on one stable identity per thing without ever falsifying what was recorded at the time.

**Decision.** `elements.id` / `relationships.id` are server-generated UUIDs, assigned once, never reused even after retirement. `element_aliases`: `id`, `element_id`, `alias_value`, `alias_type` (`name`/`code`/`external_ref`/`source_system_key`/`merged_id`), `source`, `confidence`, `created_at` — populated both manually ("also known as") and automatically (the capture pipeline records the exact string it matched, even on a confident match, so future documents using that string match instantly without re-running fuzzy logic).

Capture matching strategy, in order, stopping at the first hit above threshold:
1. **Exact id** — the source document already carries an Atlas id (e.g. a round-tripped export).
2. **Alias exact match** — a normalised token matches an existing `alias_value`.
3. **Name + context** — fuzzy name similarity above a threshold, *and* matching type, *and* matching structural context (same parent capability/system) — context is required, not optional, specifically so "Portal" the system doesn't match "Portal" the container under an unrelated system.
4. **No match** → propose a new element. Never silently create — a capture-draft `create` delta is exactly this case, always human-reviewed (ADR-004).

`merges`: `id`, `org_id`, `model_id`, `surviving_element_id`, `merged_element_id`, `decided_by`, `decided_at`, `rationale`, `evidence_ref` (nullable). On merge, `merged_element_id`'s own row is retired (not deleted); every existing relationship and delta that referenced it is left untouched, because rewriting them would falsify what a past commit — or an already-cited tagged version — actually said. Instead `merged_element_id` becomes a permanent alias (`alias_type = merged_id`) of `surviving_element_id`, and every lookup path (materialisation, search, relationship-rule checks) resolves ids through the alias table, so the two ids behave as one from that point on.

**Alternatives rejected.**
- *Rewriting historical rows to point at the surviving id* — falsifies history and any already-cited tagged version.
- *Fully automatic merge above a confidence threshold, no human step* — identity merges are exactly the kind of judgement call the product wants recorded with a rationale, not hidden.

**Consequences.** "Resolve through the alias table" has to be one shared function/view used everywhere an element is looked up by id — if any code path looks elements up directly instead, the alias table becomes decorative. This is an implementation-discipline risk worth calling out now, not a schema risk.

## ADR-009: Tenancy and access

**Context.** Multi-organisation, multi-role access, sized realistically for one-or-two-architect teams, with occasional need to share a specific version outside the organisation (e.g. an FOI request, an external auditor).

**Decision.** Every model-bearing table carries `organisation_id`; Postgres row-level security policies scope all reads/writes to the caller's organisation membership, enforced at the database layer as defense in depth, not only in application code. `organisation_members`: `org_id`, `user_id`, `role`, `invited_by`, `joined_at`.

Four roles, chosen to degrade gracefully for a one-person team: **Owner** (org/billing admin, implicitly also Architect), **Architect** (read-write on all model content; can approve merge requests and create tags/versions), **Contributor** (can create/edit change branches, run captures, comment; cannot merge to `main` or create tags), **Viewer** (read-only on `main` and on any tag/version, and on to-be views of branches explicitly marked shared-for-review; cannot see draft change branches or `capture_draft` branches, and sees a comment only when its own anchor is visible to them — ADR-010's Sprint M1a amendment dropped the separate internal/team visibility split this row originally named). A solo architect simply holds Owner+Architect on their own org — the model has to work with one person holding every right, not assume separation of duties (Preface #7).

Cross-organisation sharing of a specific version is a distinct grant, not a change to `organisation_id`: `model_shares`: `id`, `model_id`, `tag_id` (nullable — null means "always current `main`," set means "this version only"), `shared_with_org_id`, `permission` (`view_only`), `expires_at` (nullable), `created_by`. RLS policies allow access when `organisation_id` matches the caller's org **or** a matching non-expired `model_shares` row exists.

**Alternatives rejected.**
- *Application-layer-only tenancy checks* — one missed `WHERE` clause in one endpoint leaks across organisations; RLS makes the database the enforcement point of last resort.
- *A single "shared" boolean on models* — can't express "share only this tagged version, not live drafts," which is exactly the audit/FOI use case public-sector customers need.

**Consequences.** Every new table added to the product must get `organisation_id` and an RLS policy on day one — worth a lint rule or migration checklist, not a one-off decision each time.

**Amended (Sprint M1a, `atlas.profiles`, `supabase/migrations/20260906230000_profiles.sql`).** This ADR's tenancy model has always let one member see another exists (`members`), but nothing ever let one member see anything *about* another — no display name, no avatar, nothing beyond a bare `user_id`. `atlas.profiles` (`user_id` pk, `display_name`, a global lowercase `handle` defaulted from the email's local part at first membership, `avatar_url`) is the first table that changes that, and it is deliberately narrow: readable by any fellow org member regardless of role, editable by its own user only, and — the load-bearing constraint — **carries no email column and never will**. A handle derived once from an email at signup is not a standing channel back to that email; nothing in this schema, this table included, ever hands a member's real address to another member. This is the identity primitive @mentions (ADR-010's Sprint M1a amendment) reads; a member directory or invite UI built on top of it is explicitly deferred (SPEC §11, target U4) — this amendment is the data shape, not the screen.

**Amended (Sprint 7j item 1, model archive/delete, `supabase/migrations/20260911040000_model_archive.sql`).** Model lifecycle management this ADR never covered. `models.archived_at` (nullable timestamp) is soft: an owner or architect can set it (`atlas.archive_model`) or, owner only, clear it (`atlas.restore_model`) — narrower than archive, since undoing a hide is a bigger claim than making one. Archiving changes nothing about the model's own content, cascades nothing, and hides it only from `listModelsForOrg`'s ordinary list and `OrgHome.tsx`'s own display — a direct link to an archived model still resolves, read-only, for anyone who could already see it; RLS on `models` itself is unchanged. Delete (`atlas.delete_model`, owner only, only when `archived_at` is set — checked inside the function, not left to RLS) is hard: it removes the model and every row scoped to it across the tables the real FK graph touches (commits, deltas, branches, tags, sources, aliases, facts, `elements_head`/`relationships_head`, views and their layouts/annotations, merge_requests, resolved_conflicts, comments and their mentions/notifications), in dependency order, after nulling every self-referencing or cross-table column that would otherwise make that order impossible to express (the function's own comment has the full table-by-table reasoning — of everything with a `model_id` foreign key to `models`, only `branches` itself was ever declared `on delete cascade`; nothing else is, and several of the rest are self-referencing). `models_update`'s and `models_delete`'s own grants are narrowed to specific columns (`name`/`slug`/`description`) and revoked entirely, respectively, so `archived_at` and a model's actual removal are reachable only through these two functions, never a raw client write.

The member-directory/invite-UI deferral above is still open — targeted at Sprint 7j item 2/3 (a separate PR from this one), not closed by this amendment.

**Amended (Sprint 7j item 2, organisation settings, `supabase/migrations/20260911050000_organisation_settings.sql`).** Closes the member-directory half of the deferral just above (SPEC §11's row is updated to match; invite-by-email is still open, targeted at Sprint 7j item 4). `organisations_update`'s and `members_update`'s blanket grants are narrowed the same way the previous amendment narrowed `models`': `organisations` to `name`/`slug` only (never `created_by`/`created_at`), `members` to `role` only (never `org_id`/`user_id`/`invited_by`/`joined_at` — identity and history, not settings). `organisations_delete`'s blanket grant is revoked entirely; the only path left is `atlas.delete_organisation` (owner only, checked inside the function ahead of a `models` row count — refuses with a structured `{status:'has_models', count}` rather than a raw foreign-key error when the organisation still has models, matching `atlas.delete_model`'s own "route destructive actions through one function" convention). No RLS changes: `atlas.guard_last_owner` (pre-existing, this ADR's own §3.2) already fully enforces that an organisation always keeps at least one owner, on both a role-changing `members` update and a `members` delete — this sprint adds no new server-side rule there, only a settings screen (`/o/:org/settings`, `src/ui/orgs/OrganisationSettingsView.tsx`) that lets an owner trigger the update/delete the trigger was already guarding, and surfaces its refusal as a visible error rather than a silent failure.

**Amended (Sprint 7j item 4, invite by email, `supabase/migrations/20260911060000_invites.sql`).** Closes the member-directory/invite-UI deferral in full (SPEC §11's row is fully closed to match). `invites` (`id`, `org_id`, a lowercase-normalised `email`, `role`, `invited_by`, `created_at`, nullable `consumed_at`/`consumed_by`) is owner-only to create/view/revoke (RLS mirrors `members_insert`/`members_select`/`members_delete` exactly), with a partial unique index refusing a second *pending* invite to the same email at the same org — a resend, not a new row, surfaced by `createInvite` as `{status:'already_pending'}` rather than a raw conflict. No email is ever sent (this product has no email-sending mechanism anywhere, and `atlas.profiles`' own amendment above is explicit that it never will just to expose one); an invite is consumed automatically the moment the invited email establishes a session, by whichever of two paths applies. `atlas.consume_invites_for_new_user` fires `after insert on auth.users` — the first trigger in this schema on `auth.users` itself, rather than on a `public`/`atlas` table the way every earlier trigger (`atlas.profiles`' own `atlas.ensure_profile` included, which fires on `members` insert, not `auth.users`) does; flagged here as a real schema addition, not a shortcut, per this sprint's own plan. That trigger alone only covers a fresh signup, though: an invite sent to an email that *already has an account* would otherwise sit unconsumed forever, since `auth.users` insert fires exactly once, at that account's original signup, long before such an invite could exist. `atlas.consume_my_invites` — a thin, `security definer` RPC wrapping the same shared `atlas.consume_invites_for_user` worker, called against the now-authenticated `auth.uid()` rather than a client-supplied email — closes that gap; `AuthProvider.tsx` calls it once on every real `'SIGNED_IN'` event (not a token refresh). This second path is genuinely new beyond the plan's own literal wording (which named only the signup trigger) — recorded here as a small, clearly-scoped extension rather than an unrecorded decision, since without it "invite someone who already uses Atlas" would silently do nothing.

**Amended (Sprint F7 item 4, cross-org model sharing, `supabase/migrations/20260916020000_model_shares.sql`).** This ADR named `model_shares` in its original text (above) but never migrated it — SPEC §9.2/§9.3/§9.5 carried three "pending `model_shares`" annotations ever since (Sprint H1). This sprint builds the table and RLS almost exactly as originally decided: `id`, `model_id`, `tag_id` (nullable — null is "always current `main`," set is "this version only"), `shared_with_org_id`, `permission` (`view_only`, `check`-constrained, no other value has ever existed), `expires_at` (nullable), `created_by`; a `unique (model_id, shared_with_org_id, tag_id)` index, and a trigger (`atlas.guard_model_share_not_same_org`) refusing a model shared with its own organisation, since a cross-table check can't be a plain `check` constraint. Two deviations from the original decision's own wording, both resolved in the F7 plan rather than left to drift: (1) **create/revoke a share is owner-only** on the model's own org, not the architect-inclusive floor `models_update` uses elsewhere — exposing a model outside the organisation is judged a bigger, harder-to-undo-safely decision than an ordinary content edit, the same tier `models_delete` already sits at; (2) **a specifically-shared tag, not every tag, becomes visible** to a shared-with org — `tags_select` gains a clause matching only a share's own pinned `tag_id`, never a blanket "any share on this model reveals every tag" rule, so an unpinned (main-only) share never leaks a model's separate tagged versions. `atlas.model_shared_with_me`/`atlas.commit_shared_with_me` (both `security definer`, reading `model_shares` and `members` directly, matching every other cross-table RLS helper in this schema) extend `models_select`/`commits_select`; `elements_head`/`relationships_head`/`facts`/`deltas` need no direct change, since their own RLS is already "visible iff its `commits` row is."

One new, narrow crossing of `organisations_select`'s own boundary was needed that the original decision didn't anticipate: naming a share's target organisation. `organisations_select` (`atlas.is_member(id) or created_by = auth.uid()`) means a client can never resolve an arbitrary organisation by id or slug unless already a member of it — correct for the ordinary case, but it leaves an owner with no way to turn "the org named by this slug" into an id when creating a share, or "this share's `shared_with_org_id`" back into a name when managing their own share list afterwards. Two new, deliberately narrow `security definer` RPCs close each direction: `atlas.resolve_organisation_for_sharing(p_slug)` returns only `id`/`name` for any slug, to any authenticated caller — the real gate stays `model_shares_insert`'s own owner-only check on whatever id a caller resolves this way, so a broad grant here concedes nothing; `atlas.list_share_target_org_names(p_model_id)` returns names only for shares that already exist on a model the caller owns (the ownership check is inline in the function, not left to the caller), so it has no id-enumeration surface at all. Neither function exposes anything beyond a name — no membership, content, or other organisation metadata crosses the boundary either way.

**The consultant case** the F7 prompt named explicitly — one person working across several client organisations — has two supported shapes, and this amendment records both so a future reader doesn't have to reverse-engineer which one a given setup is using. **Multi-org membership** (already possible, unrelated to this amendment): the consultant holds a `members` row in each client org directly, sees each in their own org switcher, and needs no `model_shares` row at all — the natural fit when the consultant works inside each client's own organisation as a named collaborator. **Sharing into the consultant's own org** (what this amendment newly enables): each client grants a `model_shares` row from their own model to the consultant's single organisation, without the consultant ever becoming a member of any client org; the consultant's one org then lists every client model, read-only, under `OrgHome.tsx`'s "Shared with us" section, each labelled with its owning organisation's name. This shape fits an external consultant who should never hold write access or see a client's member list, invites, or settings — exactly the boundary `model_shares`' `view_only` permission and its owner-only grant were built to hold, and the shape the prompt's own "one person, several client orgs" wording describes most directly.

**Amended (Sprint F7 item 7, `supabase/migrations/20260916040000_shared_model_access_fixes.sql`).** Exercising the golden path end to end surfaced two real gaps in the migration above, both fixed here rather than left for a later sprint: (1) `organisations_select` had no `model_shares`-aware clause at all, so `listModelsSharedWithOrg`'s own second query (resolving the owning organisation's name for "Shared with us") silently returned nothing for it, and every shared model dropped out of that list entirely for exactly the audience the feature is for — closed with `atlas.org_shares_a_model_with_me`, the same shape as `atlas.model_shared_with_me`, added as a third `organisations_select` clause. (2) An **unpinned** share gave a shared-with viewer no RLS path to discover which commit is currently main's head at all: `models_select`/`commits_select`/`tags_select` all key off an already-known commit id, but `branches` (the one table that actually stores `head_commit_id`) stayed fully member-scoped, untouched by the original migration. A tag-pinned share never hit this (the pinned tag's own `commit_id` is already visible via `tags_select`'s clause) — only "current main" was affected, which is to say the more common, default case. Resolved with a narrow RPC rather than widening `branches_select` itself: `atlas.get_shared_main_branch` returns the real main-branch row, gated on holding a share with `tag_id is null` specifically, so a tag-pinned share can never see main's live head move out from under the version it pinned; `src/db/branches.ts`'s `getMainBranch` calls it only as a fallback once the ordinary RLS-gated read comes back empty, so every existing caller (`useMainBranch`, `resolveRef`'s `main` case, and everything built on either) benefits with no call-site change of its own. `branches` itself gains no other new reachable surface — change branches, `capture_draft`, and everything else on that table stay exactly as invisible to a non-member as before.

**Amended (Platform administrator, `supabase/migrations/20260917030000_platform_admin.sql`, resolved with the human directly).** Everything above in this ADR is org-scoped — four roles, every model-bearing table carrying `organisation_id`, RLS enforced per organisation. This amendment adds Atlas's first **cross-org** role, needed once `platform_config` (E4 follow-up, application-level LLM proxy settings) existed but had no one who could safely be granted access to it: it can hold a live secret (an Anthropic API key), so it was deliberately left with no client access of any kind rather than exposed through an ill-fitting org-scoped check.

A platform admin is a fact recorded in a new, dedicated `platform_admins` table (`user_id`, `granted_by`, `granted_at`) — **not** a boolean column on `atlas.profiles`, despite `profiles` being the one existing table with no `org_id` (a person's identity already follows them across every org, the same shape this new role needed). Rejected because `profiles_select`'s own RLS makes a profile visible to *any* fellow org member — a flag there would leak "who is a platform admin" to every org-mate of every admin, a real information disclosure this schema has no precedent for accepting elsewhere. `platform_admins` instead matches this schema's own established idiom (presence in a table is the fact, the same shape `members` already uses for org membership), with a self-row-only select policy — the only thing any client can ever learn from it is its own status, never anyone else's.

Granting or revoking the role has no self-serve path and no UI: a one-off `insert`/`delete` against `platform_admins`, run as the service role (`docs/PLATFORM-ADMIN.md`), the same deliberate convention `platform_config` itself already established for exactly this kind of sensitive, low-frequency, no-existing-approver-anywhere action. Two `security definer` RPCs (`atlas.get_platform_llm_config`/`atlas.set_platform_llm_config`) are the only client-reachable path into `platform_config`'s own `'llm'` row — that table gets no new RLS policy of its own, staying exactly as locked down as before this amendment. Neither RPC ever returns the raw API key (only whether one is set); `set_platform_llm_config` leaves an existing key untouched unless a new one is supplied or explicitly cleared, so the new `/platform-admin` page never displays or round-trips a live secret.

Deliberately out of scope here, named rather than silently absent (CLAUDE.md rule 7): there is no UI to grant or revoke *other* platform admins, and platform-admin status gates nothing in this product except the one `/platform-admin` page. Both are real, natural follow-ups if a second use for this role ever appears, not implied to already exist.

## ADR-010: Comments

**Context.** Comments need to anchor to anything in the model, thread, resolve without disappearing, and survive a merge without needing special re-anchoring logic.

**Decision.** `comment_anchors`: `comment_id`, `anchor_type` (`element`/`relationship`/`delta`/`branch`/`decision`), `anchor_id` — one anchor per comment. `comments`: `id`, `org_id`, `model_id`, `parent_comment_id` (nullable — flat reply chain, no deeper nesting, matching the small-taxonomy philosophy for this feature too), `author`, `body`, `visibility` (`team`/`internal` — internal is hidden from Viewer per ADR-009), `status` (`open`/`resolved`), `resolved_by`, `resolved_at`, `created_at`.

**Resolution** never deletes or hides a thread (aside from the Viewer visibility rule) — it's a reversible status, fully visible in history.

**Survival across merges** falls out of ADR-002/008 for free: a comment anchored to an `element_id` or `relationship_id` survives because those ids never change; a comment anchored to a `delta_id` on a change branch survives a merge with zero re-anchoring logic, because a merge commit incorporates the branch's existing delta rows by ancestry (ADR-002's two-parent commit model) rather than copying them — the delta the comment points at is the same row before and after merge.

**Alternatives rejected.**
- *Anchor comments to (view_id, x, y) diagram coordinates* — coordinates are layout (ADR-011), which is explicitly non-authoritative and can be regenerated at any time; a comment anchored only to a point that can vanish on re-layout is fragile. An optional coordinate *hint* for where to visually pin a comment on a given view is fine; the real anchor is always a model object.

**Consequences.** `comment_anchors.anchor_id` is polymorphic and Postgres can't natively foreign-key it — needs either a per-`anchor_type` check constraint or a trigger to keep it honest; an implementation detail to settle later, not a blocker here.

**Amended (Sprint M1a — `supabase/migrations/20260906240000_comments.sql`, SPEC §3.8/§9.4).** What actually shipped diverges from this decision in four ways, each a real, considered change rather than a drift: (1) no separate `comment_anchors` table — `anchor_type`/`anchor_id` are inline columns on `comments` itself (S-16, recorded when the capability-maps ADR claimed the ADR-012 number this draft had reserved); (2) `anchor_type`'s values become `element`/`relationship`/`change`/`decision`/`version` — `branch` renamed `change`, `delta` dropped with no replacement yet (so the attribute-level "comment on this value" anchor UI-principles §7.1 describes isn't reachable until one lands), `version` added (anchors to a `tags` row — this product's "version," ADR-002); (3) `visibility` (`team`/`internal`) is dropped for now — no product need for an internal-only comment has shown up, and re-adding it later is a column, not a redesign; (4) **@mentions and their notifications** (this ADR never covered either): `comment_mentions` (`comment_id`, `user_id`) and `notifications` (`user_id`, `kind`, `comment_id`, `read_at`) are written together, atomically, by trigger `atlas.process_comment_mentions` parsing `@handle` out of a comment's body against `atlas.profiles.handle` (ADR-009's Sprint M1a amendment) — in-app only, no email, one notification per resolved fellow-org member, none for the author's own handle. Resolve permissions also narrow past this ADR's original text: an owner/architect resolves any thread, but so does a contributor, for a thread *they themselves started* — SPEC §9.4 has the enforcement (`atlas.guard_comment_update`).

## ADR-011: Diagrams are derived views; layout is a hint

**Context.** The thesis is explicit: no view is hand-drawn, and diagrams decay into stale, disconnected pictures in every incumbent tool. Positions have to be preserved for usability without becoming a second source of truth.

**Decision.** A **view** is a saved query, not a saved drawing. `views`: `id`, `model_id`, `kind` (`landscape`/`context`/`container`/`capability_map` — a fifth kind, `component`, existed until ADR-001's own S1 item 18 amendment removed the component level entirely), `scope_element_id` (nullable — e.g. which System a container view is "for"), `branch_id` (which branch's folded state to render; defaults to `main`'s head), `created_by`, `name`. Rendering runs the scope+kind query against the chosen branch's materialised state (ADR-003) and lays it out; no view stores its own node/edge list. `capability_map` renders the model's own capability elements and their `supports` edges — it is its own view kind alongside the other three, not the separate versioned starter-content concept in SPEC §3.10 (ADR-012), which only ever seeds elements for a view to later render.

`view_layouts`: `view_id`, `element_id` (or `relationship_id` for edge routing), `x`, `y`, optional bend points — purely a rendering hint. The litmus test for whether something belongs here: deleting every `view_layouts` row for a view and re-running the auto-layout must be lossless. If losing it would change what the organisation knows, it isn't a layout hint and doesn't belong in this table.

Free-form annotation (callouts, highlights, arrows drawn directly on a diagram for a stakeholder presentation) is a real, common ask and is supported deliberately: `view_annotations`: `view_id`, `kind` (`text`/`highlight`/`arrow`), `geometry`, `text`, `created_by` — explicitly and permanently presentational, never contributes a fact, never appears in a "the model" export, and rendered with a visually distinct style (e.g. a sticky-note affordance) so it's never mistaken for a recorded fact.

**Alternatives rejected.**
- *Let dragging one box onto another on a diagram create a relationship* — conflates a drag gesture with a reviewed fact. May return later as a UI fast-path, but it would still create an ordinary delta for review, not write the model directly from the canvas.
- *No annotation support at all* — too austere for a real presentation use case; the risk of confusion is manageable through clear visual separation instead.

**Consequences.** Any export/print of a view needs to visually distinguish generated content from annotations (e.g. a legend or watermark), so a printed diagram cited in a decision (ADR-013) can't be mistaken for more authoritative than it is.

## ADR-012: Capability maps as versioned starter content

**Context.** Sector starter maps need their own versioning and provenance, independent of any one organisation's model, and tailoring them shouldn't sever the link back to the source.

**Decision.** `capability_map_templates`: `id`, `sector` (one of `src/contracts/capabilityMapContent.ts`'s `SECTORS` — `local_government_scotland`, `local_government_england`, `nhs`, `housing`, `hei`, `public_body`, `utility`, `electricity_network`; the list lives in the contract, not a database CHECK, per ADR-001's taxonomy-in-code — amended from the original five, where `local_government` was Scottish-authority-shaped and is now a deprecated alias for `local_government_scotland`, and `generic` was renamed `public_body`), `version`, `published_at`, `source_description`, `status` (`draft`/`published`/`deprecated`). `capability_map_template_items`: `id`, `template_id`, `code`, `name`, `description`, `level`, `parent_code` (nullable).

Applying a template to an organisation's model is a `template_seed`-kind commit whose deltas are ordinary `create` deltas with `source = template:{template_id}:{version}` and `confidence = high` — a curated reference, not an AI guess, but still an ordinary, auditable fact per ADR-007, not a special-cased import path.

**Tailoring** proceeds as ordinary edits (rename/add/retire/re-parent), but a rename preserves the original template code as an `element_aliases` row (`alias_type = template_code`) rather than overwriting it, so a later template version can still be matched back against this org's (renamed) capability.

**Template upgrades** never touch an org's model automatically. An org can request a diff between the template version they have and a newer one (matched through the alias table), and, if accepted, apply it as an ordinary proposed change branch through the same review queue as any other change (ADR-006) — never a silent overwrite.

**Provenance of the map itself** lives on `capability_map_templates.source_description`, with an optional `capability_map_template_sources`: `template_id`, `citation`, `url`, `reviewed_by`, `reviewed_at` for sector bodies that need to cite the actual reference frameworks and reviewers behind a starter map — public-sector procurement will ask "where did this taxonomy come from," and the answer needs to be a citation, not "the AI produced it."

**Alternatives rejected.**
- *Hard-coding starter maps into application code* — they need independent versioning, review, and citation on a different cadence than the product's release cycle.
- *Copying template items into an org's model with no reference back* — makes future template upgrades, and "why do we have this capability," unanswerable.

**Consequences.** Template content becomes a maintained content product in its own right, likely owned by a domain expert rather than engineering — an organisational consequence, not just a schema one.

## ADR-013: Decisions and evidence

**Context.** The brief's own thesis names "decisions with arguments" as part of the wedge, and requires decisions linked to changes, elements, assumptions, and evidence — not on the "cover at minimum" list, but too central to the differentiation to leave unaddressed.

**Decision.** `decisions`: `id`, `org_id`, `model_id`, `title`, `statement`, `status` (`proposed`/`accepted`/`superseded`/`rejected`), `decided_by`, `decided_at`, `branch_id` (nullable — the change branch this decision governs, if any), `superseded_decision_id` (nullable — a decision is never deleted, only superseded, matching the append-only discipline everywhere else in this document).

`decision_arguments`: `id`, `decision_id`, `stance` (`for`/`against`/`neutral`), `body`, `author`, `created_at` — a lightweight structured pro/con list, so a decision's rationale is scannable rather than archaeology through a comment thread.

`decision_links` (polymorphic, mirroring `comment_anchors` in ADR-010): `decision_id`, `linked_type` (`element`/`relationship`/`change_branch`/`assumption`/`evidence`), `linked_id`.

`assumptions`: `id`, `model_id`, `statement`, `confidence`, `status` (`open`/`validated`/`invalidated`), `owner`, `created_at` — first-class and independent of any one decision (an assumption can be linked from several decisions; when its status changes, e.g. it's later invalidated, the linked decisions get a re-review nudge rather than being silently marked wrong).

`evidence`: `id`, `model_id`, `kind` (`document`/`link`/`capture_job_ref`/`comment_ref`), `pointer`, `description`, `added_by`, `added_at`.

**Alternatives rejected.**
- *Fold decisions into comments (a "pinned thread" is a decision)* — decisions need their own status lifecycle and typed links to assumptions/evidence that a comment thread doesn't model well; conflating them would make comments heavier than ADR-010 wants and decisions lighter than the brief's thesis wants.
- *Treat assumptions as just another decision argument* — assumptions need an independent lifecycle, revisitable even before any decision built on them is finalised.

**Consequences.** This is the least-specified area of the brief relative to its stated importance. What's fixed here is only the data shape needed so nothing built for changes, comments, or provenance has to change later; the workflow (what "closing" a decision looks like, what a re-review nudge actually does) needs its own follow-up ADR once the UI is designed.

## ADR-014: Package boundary with the existing suite

**Context.** Atlas reuses a sibling suite's philosophy (small taxonomies, no scope creep, AI-assisted capture with human review) and some of its infrastructure, but is a separate product. The boundary needs to be drawn without either duplicating real infrastructure or prematurely generalising Atlas-specific domain logic.

**Decision.** Extract into a shared package only what is genuinely domain-agnostic:
- **Graph editor primitives** — node/edge rendering surface, pan/zoom/selection, a layout algorithm wrapper. The layout algorithm has no notion of "capability."
- **Schema validation and versioning** — the generic mechanism of "a jsonb payload validated against a named, versioned schema" (the `type_schemas` idea from ADR-001) is infrastructure; the actual field definitions for Capability/System/Container/etc. are not.
- **Versioning/delta engine primitives** — the generic commit/branch/tag/replay-and-validate mechanics (ADR-002/003), parameterised over "what is a delta, how is one folded." If the existing suite has any notion of drafts or history, this is likely reusable as-is; if it doesn't yet, build it here first and extract once a second real consumer exists rather than generalising speculatively.
- **LLM proxy** — provider auth, rate limiting, per-organisation cost attribution, prompt/response logging for audit. None of this is EA-specific, and the existing suite's own AI-assisted capture is an obvious second consumer *today*, not a hypothetical future one — recommend extracting this immediately rather than waiting, unlike the graph/versioning primitives above.

**Not extracted** — stays in this product: the taxonomy itself (element/relationship types, attribute schemas, `relationship_type_rules` content); the RLS/organisation/roles model (even if the suite has its own organisations, merging tenancy models is a materially bigger and riskier decision than sharing UI/infra primitives, and shouldn't be smuggled into this ADR — see the open question below); capture-pipeline prompts and extraction logic (tuned to this taxonomy, not reusable as-is even where the LLM proxy underneath is shared); and the review-queue, decisions, comments, and capability-map-template features, all of which are product-specific.

**Alternatives rejected.**
- *Extract everything speculatively before Atlas ships anything* — guarantees the shared package's API is designed against zero real usage.
- *Keep everything in-product and duplicate later if needed* — the right default for most of the list above, but not for the LLM proxy, where the duplication cost is already obvious and immediate.

Concretely, `platform_config`'s `'llm'` row and both RPCs (`atlas.get_platform_llm_config`/`atlas.set_platform_llm_config`) gained a `provider` field, and `/platform-admin`'s picker (`LLM_PROXY_PROVIDER_OPTIONS`, `src/ui/admin/useLlmProxyConfig.ts`) is a real, data-driven select rather than a disabled label — but `set_platform_llm_config` still rejects any value but `'anthropic'`, and `llm-proxy`'s own routing (`callAnthropic`) is untouched. Nothing about *what this port does* changed: Des-Studio's own `llm-proxy` genuinely does route to OpenAI and a multi-model gateway (this ADR's earlier paragraph above), so "Anthropic only" was always a scope decision about this port, not a technical ceiling — this amendment keeps that scope decision reversible at the config layer without pre-building the routing logic itself, which stays exactly as out of scope as before. Adding a second provider for real is still a separate, larger change (new request/response shaping per provider in the edge function, a wider allow-list here, a second set of model options) — this amendment only removes the schema migration that change would otherwise need.

## ADR-015: Head materialisation is a security-definer function, not application code or a SQL reimplementation of fold

**Context.** `elements_head`, `relationships_head`, and `facts` (ADR-003, ADR-007) are materialised projections: something has to run the fold algorithm (SPEC §6) and write the result whenever a commit lands, and that "something" was never actually built in Sprint F1 — its migrations created these tables with no insert/update/delete grant for `authenticated` at all, correctly anticipating that populating them "means running the fold algorithm, which belongs to src/engine, not to a migration or a client's own judgement" (the projections migration's own words), but nothing was ever added to do that running. Sprint U1's editing step (step 5) needed this fixed first, and needed it before the element page (step 3) could show anything real.

**Decision.** `atlas.commit_deltas` (`supabase/migrations/20260906090000_facts_and_commit_deltas.sql`) is now the one place a commit is written. It is `security definer`, taking over a role the plain `commits`/`branches` RLS policies deliberately never granted an ordinary session: advancing `main` directly. (`commits_insert`'s policy from Sprint F1 step 2 requires `branch.kind = 'change'` and a `draft` status — main was never a legal target for a direct client insert, on the assumption that only a future `atlas.merge_branch`/`atlas.seed_from_map` would advance it, per SPEC §5.3's "who writes commits" table.)

This is a **permanent** product decision, not a stopgap for the sprint that happens to have no branch UI yet: **a contributor never commits to main, whether or not a branch/review-queue UI exists; owner/architect may, always.** `commit_deltas` re-derives this from `auth.uid()` itself — branch-kind-dependent (`owner`/`architect` only when the target is `main`; `owner`/`architect`/`contributor`, matching `commits_insert`'s original rule, for a `change` branch, which must still be `draft`) — rather than trusting anything the caller claims, since being `security definer` means it no longer gets any check for free from the bypassed policy. UI-principles.md §4.2 is amended to match: `Edit` on `main` is available to owner/architect directly, and reads `Propose a change…` for a contributor there; "there is no editing at main, ever" is no longer this product's rule for every role, only for contributors.

In one transaction: insert the commit and its deltas, advance `branches.head_commit_id` (still checked by `atlas.guard_branch_head_advance`, unchanged since Sprint F1 step 6, which supplies the actual concurrency guarantee — `commit_deltas` adds no separate check of its own), and — only when the branch is `main` — materialise the three projection tables via `atlas.replace_main_head_projection`, a second, narrower `security definer` function with no grant to `authenticated` at all (only `commit_deltas`, calling it as its own owner, and `service_role`, for `rebuildHead`'s repair/verification path, can reach it). What used to be a two-round-trip insert-then-compare-and-swap (`src/db/commits.ts`, Sprint F1 step 6) with a documented "a lost race leaves a harmless orphan commit" tradeoff is now one call: a lost race means the whole transaction fails and nothing was written, because a PL/pgSQL function body is one transaction. The orphan-commit tradeoff this ADR removes was itself recorded as accepted-for-now in Sprint F1's step 7 Definition-of-Done review (`docs/SPRINT-F1-STATUS.md`); it no longer applies.

**The original design computed the resulting `Head` client-side and shipped it as data, not as SQL to execute** — `src/db/commits.ts` folded with the existing, tested `src/engine` (it already did this for validation) and serialised the result (`src/engine/projection.ts`) into the jsonb arrays `commit_deltas`/`replace_main_head_projection` wrote verbatim, so the fold/apply algorithm itself was never reimplemented in SQL. This was a real tradeoff, not a free lunch: the full projection for the new head crossed the wire on every commit to `main`, sized to the model's live element/relationship/fact count regardless of how small the actual delta was (adding one system to a 2,000-element landscape still sent all 2,000 elements' rows back). It was deliberately the simpler design at first, matching SPEC §6.5's own "fetch everything" allowance and this product's stated scale (one or two architects, not a live-editing crowd). Sprint U1 step 4's Playwright perf test (a generated 2,000-element model, UI-principles.md §8.6) is where this got a real number: against the fixture's 2,010 elements / 6,000 relationships / ~16,000 facts, the real serialised payload for one attribute edit measured ~8.45 MB, budgeted at 12 MB.

**E3 amendment (docs/prompts/atlas-prompt-pack.md) implements the upgrade path named above, exactly as scoped**: `atlas.apply_deltas_to_main_projection` (`supabase/migrations/20260913100000_delta_apply_in_sql.sql`) applies just the *new* commit's deltas directly against the existing `elements_head`/`relationships_head`/`facts` rows for the previous head — copying that previous snapshot forward under the new commit id, then patching it per delta (`jsonb_set`/`-` for a jsonb attribute, a direct column write for `name`/`parentId`, insert/delete for create/retract) — rather than receiving and replacing the whole materialised set. This is SPEC §6.5's own incremental-rebuild shape (`load(parent)` then `applyAll` just the new deltas), not the full re-fold the "alternatives rejected" section below still correctly rules out: `src/db/commits.ts`'s own client-side `fold` still runs first, unchanged, for validation — this function trusts that an already-validated, ordered delta list is what it's being handed (the same trust boundary `src/engine/deltas.ts`'s own `apply` states in its doc comment), re-checking only the two internal-consistency guards `apply` itself bakes in beyond raw mutation (a retract's own subject-exists check, and C8 — no live relationship may still reference a retracted element).

Scoped deliberately, not silently: this covers `element`/`relationship` `create`/`update`/`retract` — exactly the three actions E8's own perf measurement names (add system, add relationship, save attribute) — but not `restore`. Restoring something retracted in an *earlier* commit needs that attribute's last-known value reconstructed from the model's full delta history (`deltas` is append-only, CLAUDE.md rule 5, but the retract already deleted the live projection rows this function would otherwise copy forward) — a materially harder problem, deliberately deferred. `src/db/commits.ts` still sends the full client-computed projection (the pre-E3 path, unchanged) for any commit containing a restore delta; `merge_branch`/`seed_from_map` are also unaffected — both still always compute and send a full projection.

The measured baseline moved accordingly: `e2e/landscape-perf.spec.ts`'s payload-size assertion now measures the actual RPC payload for a single-element edit (deltas only, since that scenario has no restore) rather than the old whole-projection serialisation, and the budget dropped from 12 MB to 200 KB — payload size for a single edit no longer scales with model size at all, so a real regression here looks like "the whole projection got sent again," not a few-percent wobble. E8 (performance, not yet run as of this amendment) is where this gets exercised end to end against real routes/actions, not just this one synthetic payload check.

**Alternatives rejected.**
- *Reimplement `apply`/`fold` (the full delta-application semantics) in PL/pgSQL, as a second, independent implementation* — duplicates already-tested engine logic in a second language, with no independent test suite of its own, for the sake of avoiding a jsonb hand-off that's otherwise straightforward. (This is different from the delta-apply upgrade path named above, which still uses the client-computed delta list, not a from-scratch SQL fold — it moves *where* the new commit's deltas get applied to the projection, not *what* computes the delta list itself.)
- *Keep the two-round-trip CAS pattern and just add a separate materialisation step after it* — doesn't fix the underlying race window, and adds a *third* round trip (and a *second* kind of partial-write, projection-without-commit) instead of removing the first.
- *Make `commit_deltas` an ordinary (non-`security definer`) function and separately loosen the RLS policies on `elements_head`/`relationships_head`/`facts`/`commits` for `main`* — would let any authenticated session with the right role write projection rows directly, without going through a fold at all; the whole point of those tables having no `authenticated` write grant is that nothing but the engine's own fold output should ever land in them.

**Consequences.** `src/db/rebuildHead.ts` (the repair/verification path, SPEC §6.6's integrity job) reuses `atlas.replace_main_head_projection` from a service-role context, driven by the same engine (`foldFromGenesis`) rather than a SQL-side refold — built alongside this ADR, not deferred; its head-equals-fold comparison lives in `src/db/repository.integration.test.ts`, the same file every other real-Supabase check in this codebase lives in, rather than waiting for a later sprint's own integration-test file. `type_schemas` (ADR-001, SPEC §3.3) is deferred to Sprint K1 rather than migrated now: as SPEC literally specifies it (a full TypeScript-type-to-JSON-Schema generator plus a checked-in seed and validator, RT-5), it is real schema-validation infrastructure the element page never needed — attribute order and per-type definitions live in `src/contracts` as code instead, and Sprint K1's capture edge function, the first consumer outside the TypeScript runtime, is what will actually need the generator.

## ADR-016: Capability `level` is computed from `parent_id` depth, never a stored attribute

**Context.** ADR-001 originally gave Capability a required `level` (1–3) attribute alongside `parent_capability_id`. SPEC §6.3's V2 validation rule only ever checked that a capability's parent, if any, is itself a capability — it never checked that a stored `level` value actually matched real nesting depth. Sprint U2's capability map (ADR-011's `capability_map` view kind) renders L1/L2/L3 straight from the `parent_id` chain (src/ui/capabilityMap/layout.ts), not from `attributes.level` — so the two could silently disagree the moment anyone edited `level` independently of moving an element, and any future code that trusted `level` for a structural decision would be trusting a fact that isn't guaranteed to be one.

**Decision.** `level` is removed from `CapabilityAttributes` entirely (src/contracts/delta.ts) — it is never stored, never part of an `element.create`/`element.update` delta, and never independently editable. A capability's level is always `1 + the number of capability ancestors above it`, computed on read from the real `parent_id` chain (src/ui/elements/capabilityDepth.ts), capped at 3 — a chain that doesn't resolve cleanly within that cap (too deep, or a parent reference that doesn't terminate) computes to `null` and is shown as a gap, the same stance src/ui/capabilityMap/layout.ts already takes on a malformed chain, rather than either guessing or hiding it.

The element page's Structure section (§4.5: "For a capability: level, parent capability, child capabilities…") shows the computed level as a plain value with no provenance badge — it isn't a fact asserted by any source, so it gets none, the same way "children" and "parent" are shown structurally without one.

**Alternatives rejected.**
- *Keep `level` as a stored, editable attribute and add a validation gate checking it matches nesting depth* — still leaves two representations of the same information that a validation bug could let drift apart; computing it removes the possibility entirely rather than policing it.
- *Drop the concept of "level" altogether* — UI-principles §3.1/§6.1 and the element page's own Structure section spec name "level" directly; the concept is real, only its storage as an independent fact was the trap.

**Consequences.** A starter capability map's `capability_map_items.level` (SPEC §3.10, ADR-012) remains a real column on the *template* content — that's about the template's own authored structure, reviewed once by a domain expert, not a live organisation's model, so it isn't subject to the same drift risk and is unaffected by this decision.

## ADR-017: Atlas has its own Supabase project and its own identity/tenancy tables

**Context.** ADR-014 drew a package boundary with the existing suite but left one question open: whether Atlas shares the existing suite's tenancy/identity tables or has entirely its own, naming it as needing "facts about the existing suite's actual schema that this document's authoring session doesn't have access to." That gap has since closed, not because this document gained new information about the existing suite's *schema*, but because its actual deployment topology became directly inspectable: docs/AUDIT-2026-09-U2.md §8.1's live Supabase organisation lookup found two entirely separate projects already exist — "Architecture" (this product, holding every migration in `supabase/migrations/`) and "Des-studio" (the existing suite, with its own 71 migrations and its own deployed edge functions, including a real `llm-proxy`). No query, RLS policy, foreign key, or edge function in this repository has ever referenced Des-studio's project, tables, or ids — ADR-009's `organisations`/`members` tables were built as this product's own from their first migration onward, not provisionally pending this decision.

**Decision.** Atlas has its own Supabase project and its own `organisations`/`members`/`auth.users` — permanently, not as an interim state awaiting a shared-identity migration. The two products are physically separate Postgres databases with no cross-database join possible even by mistake. A person who uses both products holds two independent accounts and two independent organisation memberships, exactly as if they were unrelated SaaS products, because for tenancy purposes they are.

Sharing between the two products, where it happens at all, stays exactly where ADR-014 already drew it: the extracted-package boundary (graph editor primitives, schema validation/versioning, the versioning/delta engine primitives, the LLM proxy) — code, not data, and never identity. If the two products' identity ever needs to feel unified to a user (single sign-on, one subscription spanning both), that is a product/billing integration layered on top of two separate identity stores — a shared OAuth provider, or an account-linking table referencing both by external id — never a shared `organisations`/`members` schema. That is a distinct, larger decision this ADR does not make and does not need to: it belongs in its own future ADR if a concrete requirement for it ever appears, not pre-emptively here.

**Alternatives rejected.**
- *Share `organisations`/`members` across both products* — the option ADR-014 left open pending schema facts this session didn't have at the time. Decided against now: Atlas already has real tenant data accumulated across this sprint sequence, which is exactly the expensive-after-the-fact retrofit ADR-014's own Consequences warned about, and no concrete requirement for shared identity has ever surfaced (not in the brief, not in a sprint, not from a user). Absent that, separate is the option that costs nothing to keep and everything to undo later.
- *A shared `auth.users` with per-product membership tables* — Supabase's `auth.users` is project-scoped, so sharing it means sharing the whole project, not one table. That reopens every tenancy/RLS boundary this ADR exists to keep closed: a bug in the existing suite's RLS would become a risk to Atlas's data, and vice versa.
- *Defer the decision further, pending an actual look at the existing suite's schema* — was the honest position when ADR-014 was written, with no access to the existing suite's repository. It no longer holds: the live-inspection evidence ADR-014 named as missing now exists (docs/AUDIT-2026-09-U2.md §8.1), and it already points the same way separate identity does in practice. Continuing to defer would only postpone a decision today's evidence already answers.

**Consequences.** ADR-014's "Not extracted" list (the RLS/organisation/roles model) is now unconditional rather than provisional — it was never actually going to be shared, and this ADR removes the one open question that kept that from being said plainly. The "Deferred to follow-up ADRs" section's identity/tenancy item is closed and struck from that list. No migration, RLS policy, or application code changes as a result of this ADR: it ratifies a design that was already true in every implementation decision made since ADR-009, rather than requiring a new one.

## ADR-018: A model's main branch always has a real head — the genesis commit

**Context.** From Sprint F1 onward, `atlas.on_model_created` gave every new model a `main` branch with `base_commit_id`/`head_commit_id` both null, on the assumption that the model's first real commit would set them. But nothing could: `atlas.commit_deltas`'s own lookup (`join commits c on c.id = p_base_commit_id`) requires an existing commit row to attach the new one to, so a null head was a dead end for every write path except `atlas.seed_from_map` (capability-map import), which alone was allowed to insert a commit with `parent_commit_id` null. That made seeding from a starter map the *only* way a model could ever get its first commit — not a design choice anyone had made deliberately, but a gap nobody had needed to close until "add a capability by hand from an empty model" (the empty-state feature this ADR unblocks) needed a genesis commit from a code path that has nothing to do with capability maps. Three Playwright specs and one integration-test fixture had already worked around the same gap with a direct service-role insert of a fake "genesis" commit before this ADR, each carrying a comment pointing at the same unresolved cause.

**Decision.** `commit_kind` gains a fifth value, `'genesis'` — a real commit, inserted exactly once per model, with zero deltas, `depth = 0`, and the only kind ever allowed a null `parent_commit_id`. `atlas.on_model_created` inserts it in the same transaction as the model's `main` branch and sets `base_commit_id = head_commit_id` to it immediately, so **a model's main branch never has a null head, from the instant the model exists.** The only inserter of a `'genesis'` commit is this trigger — never a client RPC, never `atlas.commit_deltas` (which already rejects any `p_kind` not in `('manual', 'merge', 'template_seed')` for a main-branch commit, so `'genesis'` was excluded automatically the moment it stopped being in that list) and never `atlas.seed_from_map` (which now requires a real parent like every other commit, described below).

`branches.base_commit_id`/`head_commit_id` become `NOT NULL` outright, replacing the two kind-conditional CHECKs from Sprint F1 (`kind <> 'main' or (... base_commit_id is null)` and `kind = 'main' or base_commit_id is not null`) with one flat rule: every branch, of every kind, always has both set. `atlas.seed_from_map` (SPEC §5.1's "the first commit of a model seeded from a capability map") is unchanged in what it does — insert one `template_seed` commit carrying the map's items as `element.create` deltas — but no longer treats that commit as a null-parent genesis: it looks up main's current head (always the genesis commit, at this point, or seeding is refused), parents the seed commit on it, and increments `depth` to 1. "Seeded once, ever" is now expressed as "the current head is still the genesis commit itself" rather than "head_commit_id is null" — the same fact, checked against a head that always exists rather than one that might not. A migration backfills a genesis commit, and repoints `base_commit_id`/`head_commit_id`, for any model created before this ADR whose main had a null head.

This closes the empty-state gap outright: `src/db/ref.ts`'s `resolveRef` always resolves `main` to a real commit id now (the third case in its own doc comment — "a model with no commits yet" — no longer arises for `main`; an unknown tag or unknown branch name still resolve to `null`, unchanged), so `src/ui/capabilityMap/useCapabilityMap.ts` always reaches `ready`, with an empty tree for a fresh model rather than `refNotFound`. "Add a capability" (`src/ui/capabilityMap/CapabilityMapAddForm.tsx`, already built) commits through `atlas.commit_deltas` like any other edit, parented on the genesis commit exactly like a starter-map seed would be — no special-casing anywhere in the write path for "this is the model's very first capability." The three Playwright specs' and one integration fixture's service-role genesis bootstraps (`e2e/landscape-perf.spec.ts`, `e2e/element-edit.spec.ts`, `e2e/capability-map.spec.ts`, `e2e/zoom-chain-structure.spec.ts`, `e2e/landscape-navigation.spec.ts`, `e2e/versions.spec.ts`, `e2e/fixtures/changeBranchFixture.ts`) are deleted; each now just reads `main.head_commit_id`, already populated the instant `createModel` returns.

**Alternatives rejected.**
- *Give `atlas.commit_deltas` its own "create a genesis commit if the branch has none yet" branch, callable by any authenticated owner/architect* — makes genesis creation a general capability of the one function every ordinary edit already goes through, rather than a fact about model creation itself; a client could then construct a `kind: 'genesis'` commit with a real parent by mistake or malice, which is exactly the "genesis means true origin" invariant this ADR exists to protect.
- *Keep `head_commit_id` nullable and teach every reader (`resolveRef`, the engine's `ancestry`/`foldFromGenesis`, every UI hook) to treat null as "identical to an empty fold" explicitly* — this is what the codebase already did, informally, everywhere except the one write path (`commit_deltas`'s own base-commit lookup) that actually needed a row to exist. Making the null case rigorous everywhere it's read is strictly more code than making it not exist at the one place it's written.
- *A dedicated `atlas.create_first_capability` RPC, parallel to `seed_from_map`, for exactly the "empty model, add one capability" case* — duplicates `commit_deltas`'s validation and projection-refresh logic for no reason once main always has a real parent to commit against; "add a capability" needed nothing seed_from_map-shaped once the actual blocker (no parent to attach to) was gone.

**Consequences.** `src/contracts/delta.ts`'s `CommitKind` gains `'genesis'`; `CommitEnvelope.parentCommitId`'s doc comment is corrected — never null in a client-constructed envelope, since a client never constructs a genesis commit. `docs/SPEC-data-model.md` §3.4/§3.5/§5.1 are updated to describe `base_commit_id`/`head_commit_id` as always-set and to describe seeding's precondition as "still at genesis" rather than "no commits yet." Every Postgres enum value addition needs its own migration, separate from the one that uses the new value as a literal (`ALTER TYPE ... ADD VALUE` isn't visible by name until its own transaction commits) — `supabase/migrations/20260906210000_commit_kind_genesis.sql` exists only for that reason, ahead of `20260906220000_main_always_has_head.sql`'s actual implementation.

## ADR-019: Identity policy for created elements — search-first, merge reversibly, and report what search missed

**Context.** A prompt pack this product's brief traces back to named three linked rules for how duplicate elements get handled — search before creating, merge duplicates reversibly rather than deleting one, and surface the duplicates search alone didn't catch — under an ADR numbering that doesn't match this repo's. Substance, not number, is what matters here: none of the three was ever actually recorded as a decision in this repo's own ADR sequence, even though the second is already most of the way into `docs/SPEC-data-model.md` (`element_merges`, `atlas.merge_elements`, ADR-008) and the first shipped this sprint (`src/ui/components/ElementSearchAdd`, the search-first "Add" control on Landscape/Container/Component). A product rule like this is exactly what CLAUDE.md means by "an undocumented choice is exactly the kind of untracked fact this product is built to eliminate everywhere else" — it counts as ADR material even though no table changes shape today. Recording it now, plainly, gives U3b's own search box (already built) and Q1's duplicates-report build something real to be *consistent with* rather than a decision made silently a second time.

**Decision.** Three rules, one policy:

1. **Search before creating, always.** Every place an element can be created goes through a search-first control (`ElementSearchAdd`) that shows existing matches by name, alias, or description before offering to create anything new — never a bare "new element" form. This is preventive, not a gate with teeth: it lowers the rate of accidental duplicates at the moment of creation, nothing more.
2. **A duplicate, once found, is resolved by a reversible merge, never a delete.** `atlas.merge_elements` (ADR-008, SPEC §3.6/§9/§7.4 — specified, not yet implemented, deferred to Q1 alongside the matching pipeline it depends on) is the only sanctioned fix: the loser retracts, the survivor inherits its relationships (deduplicated, S-6), an `aliases` row of type `merged_id` records the mapping so old references still resolve, and `element_merges` itself is an append-only record of the merge. "Reversible" names what CLAUDE.md rule 5 already requires of everything in this system — nothing is forgotten, only superseded — applied specifically to identity, not a new mechanism this ADR invents.
3. **Search-first creation alone doesn't catch every duplicate, so the model needs a standing duplicates report, independent of any one person's create flow.** Two people can each search, each find nothing, and each create the same real-world system minutes apart — search-first only ever protects the moment of creation, not the model's whole life. A periodic or on-demand report surfacing likely-duplicate elements (by the same name/alias/description similarity `ElementSearchAdd`'s own search already uses, or `elements_head_name_trgm_idx`'s trigram matching once Q1's matching pipeline exists) is the second half of this policy, resolved through the same `atlas.merge_elements` action a reviewer chooses the survivor for — not built yet, and not this ADR's job to build, but named here so Q1 builds it against a decided requirement rather than inventing one when the moment arrives.

**Alternatives rejected.**
- *Rely on search-first creation alone, with no report* — leaves the exact race condition above (two independent, well-intentioned creators) permanently unaddressed; search-first is preventive, not comprehensive, and was never claimed to be either.
- *A hard uniqueness constraint on element name* — elements in this model legitimately share names across unrelated real things (two different orgs' "Billing Service"), and the same real thing legitimately gets referred to by different names (`aliases` exists precisely because names aren't identity) — a uniqueness constraint would reject exactly the cases `aliases` was built to handle.
- *Auto-merge on a high-confidence match instead of a human-reviewed report* — identity is advisory, never blocking or automatic (S-13, ADR-005(c)): a human always chooses the survivor. A report that quietly merged for you would be exactly the identity-conflict-blocks-everything failure mode S-13 already rejected, just moved to a different trigger.

**Consequences.** No migration, no contract change — this ADR ratifies existing SPEC infrastructure (`element_merges`, `atlas.merge_elements`, `aliases.merged_id`) as *the* identity-resolution mechanism and gives the not-yet-built duplicates report a name and a place in the deferred-to-Q1 list below, rather than leaving it as a prompt-pack idea with no repo record. `ElementSearchAdd`'s own module comment is corrected to point here instead of a numbering mismatch.

**Amended (E7, `supabase/migrations/20260916050000_element_merges.sql`).** `element_merges` and `atlas.merge_elements` are built — item 2 above is no longer "specified, not yet implemented." The shape is almost exactly SPEC §3.6's own table; two decisions below aren't in that SPEC text at all, resolved here rather than invented silently mid-migration.

1. **The merge itself is an ordinary `manual` commit, not a new commit kind or a bespoke RPC that builds one.** `src/engine/mergeElements.ts`'s `buildMergeElementsDeltas` computes the retract-and-repoint delta sequence exactly as SPEC §3.6 describes (retract the loser, re-point every relationship that touched it, re-parent its children), and the client commits it through the same `commitToBranch` path — and the same role/branch-status checks — every other edit already goes through. Merging two elements is, mechanically, exactly the edit a person would make by hand; it needs no special commit-kind tier the way `preparation`/`merge` genuinely do (ADR-021 §2a). A new RPC, `atlas.record_element_merge`, exists only for the one thing a plain commit can't also do atomically: writing the `element_merges` row and the `merged_id` alias alongside it, once the commit itself has already succeeded. Two collision rules the SPEC text doesn't name, reused rather than invented: re-pointing a relationship that would duplicate one the survivor already has drops the loser's copy (S-6); re-pointing one that would collide with a cardinality limit the survivor already holds demotes it to `'secondary'` for `supports` (its one neutral value) or drops it outright for `owns` (which has none) — the identical two conventions ADR-021 §4.3 already established for the equivalent branch-merge collision. A relationship directly between the two elements being merged is dropped rather than repointed into a self-loop, which would be meaningless once they're one identity.
2. **Undo needs no new RPC, and `element_merges` is never touched by it.** The E7 prompt asks for a genuine, callable undo ("merge then undo is the identity," a real property test — see below) — this is that, but CLAUDE.md rule 5 names `element_merges` explicitly among the tables application code may never update or delete, so undo cannot mark a row "reversed" or remove it. `buildUndoMergeElementsDeltas` inverts the original merge commit's own delta list purely mechanically (restoring what it retracted, retracting what it created) into an ordinary new commit, needing no lookup beyond that commit's own deltas. `element_merges` stays a permanent, accurate historical fact — "at this point, X was merged into Y" — exactly as `deltas`/`commits`/`resolved_conflicts` already work; whether that merge is still in effect is answered the same way it's answered for everything else in this schema, by whether the merged element is currently live, not by a second column on this table.

Verified by a new generative property (P-33, SPEC §10): for a wide range of relationship/cardinality/self-loop/child combinations, merging then undoing restores a state identical to the original (element/relationship existence, attributes, parenting — never the specific delta ids, which are minted fresh and never reused, by this schema's own design).

3. **Trigram identity matching in the merge classifier is closed too.** `src/engine/trigram.ts`'s `trigramSimilarity` reimplements `pg_trgm`'s own trigram extraction and Jaccard-index formula in pure TypeScript, since `classifyMerge` compares two already-folded, in-memory `Head`s with no database round trip to lean on. `classifyMerge`'s weak "identity" finding (§7.3) now fires on similarity ≥ `IDENTITY_TRIGRAM_THRESHOLD` (0.6, SPEC §8 point 3's own value) rather than exact name equality; an exact match keeps the pre-existing same-`parentId` rule, while a fuzzy match additionally needs corroborating context — the same `parentId` for a container/capability, or (for a system/actor, which SPEC §8 itself says has no parent worth comparing) a shared vendor, a shared description, or a common owning actor.

4. **The "Merge into…" UI action is closed too, resolved with the human directly on one point SPEC didn't already answer.** The golden path's own "old name found by search" needs more than the `merged_id` alias above: that alias's value is the loser's *id*, never its name (deliberately, per SPEC §3.6, for a stale-permalink lookup), and `loadSearchPool` excludes it from search regardless — a UUID could never match a typed name either way. `atlas.record_element_merge` now writes a second, ordinary `name`-type alias too (the loser's own former name, pointing at the survivor — SPEC §3.6's own amendment), so a search for the old name resolves to the survivor the same way any other name alias already would.

   The UI itself: `ElementHeader.tsx`'s `onMerge` (omitted-not-disabled, the same `canEditBranch` gate as `onEdit`/`onRetire`/`onRemoveFromModel` — no separate role check, since a merge is mechanically an ordinary edit). `MergeIntoAction.tsx` picks the survivor via `useRelationshipTargetSearch` (restricted to the loser's own element type), requires a rationale (CLAUDE.md rule 4 — "these are the same real thing" is exactly the fact `element_merges.rationale` exists to record), and previews the real effect before confirming (CLAUDE.md rule 7 — no stand-in confirmation UI): `buildMergeElementsDeltas` (`src/engine/mergeElements.ts`) now also returns a structured `MergeEffect` alongside its deltas, classifying every touched relationship as repointed, repointed-and-demoted-to-secondary, or dropped (self-loop, S-6 duplicate, or cardinality collision) — the exact classification the real commit uses, computed in the same pass, never a second hand-written approximation of it. `useMergePreview.ts` folds the real head and calls this as a dry run; `mergeEffectSentences.ts` turns it into the plain-English list the panel shows. `useElementMerge.ts` commits, then reports a save toast with a real, working "Undo" button — `toastStore.ts` gained an optional `action` field for this (`{label, onClick}`, rendered by `ToastHost.tsx` as a second button next to Dismiss), since undo has to work from a toast that can outlive the page that started the merge, not just from the page itself.

5. **The golden path is closed too.** `e2e/golden-path-merge-elements.spec.ts` merges two near-duplicate systems (click-only from Home), confirms the loser's old name resolves to the survivor by search (the `name` alias from point 4 above), clicks the merge toast's own "Undo," and confirms the original element is reachable by its own name again afterward — distinguished from the survivor's own still-lingering alias hit by matching the exact original name text, since undo never removes that alias (CLAUDE.md rule 5 again: nothing here is ever deleted). Written and reasoned through against the real UI, like every Playwright spec this session, but not executed — this sandbox has no Docker route to a real Supabase (`pnpm db:start`).

E7 (docs/prompts/atlas-prompt-pack.md) is now fully closed.

**Amended (F4, decided ahead of any code — `docs/prompts/atlas-prompt-pack.md` "duplicates report (Q1)").** Item 3 above — the standing duplicates report — was built against five decisions this ADR's own point 3 named but didn't answer, recorded here first rather than invented silently mid-migration (this sprint's own "decide, then build" discipline, the same one ADR-023 followed for F6). The build itself landed in `supabase/migrations/20260924010000_duplicates_schema.sql` (tables/RLS/toggle), `20260924020000_duplicate_check_rpcs.sql` (the two RPCs) and `20260924030000_scheduled_duplicate_checks.sql` (the nightly sweep, item 5 below), one PR-sized step at a time, plus the UI (`src/ui/duplicates/`) and the `MergeIntoAction`/`ElementPage.tsx` prefill wiring the closing paragraph below describes.

1. **Detection is a Postgres RPC, not an edge function, and needs no LLM.** Unlike capture (K1), every signal here — name/alias trigram similarity, a shared-owner join, relationship overlap — is a plain SQL computation over `elements_head`/`relationships_head`/`aliases`; routing it through an edge function the way `capture-run` does would add Deno bundling and an async job-queue table for no reason. `atlas.run_duplicate_check(p_model_id)` runs synchronously, in Postgres, callable directly by a client and, for the nightly sweep below, by `pg_cron`.
2. **The trigram gate uses `pg_trgm`'s `%` operator, not a bare `similarity() >= threshold` predicate.** A function-call predicate in a self-join gives the query planner nothing to seek on; the `%` operator (after `set local pg_trgm.similarity_threshold = 0.6` — `IDENTITY_TRIGRAM_THRESHOLD`, SPEC §8 point 3's own value, the same constant `src/engine/trigram.ts` documents for the in-memory engine matcher the "Amended (E7, ...)" paragraph's own item 3 already covers) is what lets the self-join use `elements_head_name_trgm_idx` (already exists, `20260906071600_projections.sql`) rather than scanning every pair. Corroborating signals — shared parent, vendor, description, owner, or relationship neighbours — reuse `src/engine/merge.ts`'s `identityContextCorroborates` logic rather than a second, hand-written version of the same rule; scope is `system`/`container` only for v1 (capability/actor duplication is a different, lower-value conversation this build doesn't take on). Every threshold and the scoring formula that combines these signals are recorded in this build's own migration comment and are explicitly tunable, not derived science — the same posture E7's own prompt already took ("thresholds documented"). **Amended 2026-10-16 (duplicates fix, `20261016010000_duplicate_check_squashed_names.sql`):** the gate and `name_similarity` also compare each name and alias in its *squashed* form, `atlas.squash_name` (lower case, every non-alphanumeric removed), with its own trigram index. pg_trgm splits a string into words at spaces and punctuation, so "PowerON" vs "Power On" scored 0.545 — under 0.6 — and the report could never flag a spacing, hyphen or case variant, the commonest real duplicate (this item's own integration and Playwright tests used exactly that pair and had never passed). The threshold stays 0.6; the in-memory engine matcher (`src/engine/trigram.ts`) and capture's matching are unchanged.
3. **Three new tables — `duplicate_check_runs`, `duplicate_candidates`, `duplicate_dismissals` — none of them touched by CLAUDE.md rule 5's protected list**, since none of them is model data: they're operational tooling recording *that a check ran* and *what a human decided about a pair*, the same status as `capture_jobs`. RLS on all three is member-scoped select with no `authenticated` write grant at all — every write goes through `atlas.run_duplicate_check`/`atlas.dismiss_duplicate_pair`, both `security definer`. A merged-away or retracted element silently drops its `duplicate_candidates` row out of the report the same way it would out of any other query joined to `elements_head` at main's current head — no cleanup RPC exists or is needed. (Step 5's first cut of `listDuplicateCandidates` didn't actually do this join — a real defect Step 7's own tests caught and fixed, `src/db/duplicates.ts`'s own doc comment has the detail — so this promise is true of the shipped code, not just this paragraph's own original intent.) Un-dismissing a pair isn't offered in v1; because the table isn't rule-5-protected, adding that later is an ordinary feature addition, not a design change.
4. **The per-model on/off toggle (`models.duplicates_check_enabled`, default `false`) is a plain column grant, not an RPC.** `20260911040000_model_archive.sql` deliberately narrowed `models`' own update grant specifically because a blanket grant would have let an architect bypass a *stricter*, owner-only RPC rule (`restore_model`) elsewhere on that same table — no such asymmetry exists for this toggle, so `grant update (duplicates_check_enabled) on models to authenticated` is correct as-is, gated by `models_update`'s own existing owner/architect RLS. Chosen per-model over per-org or per-org-with-override (decided with the human): a duplicate can only ever exist within one model's own head, matching every other per-landscape control in this app (capability map, roadmap, capture), and this app's one existing org-scoped setting (`attribute_definitions`) is definitional vocabulary, not an operational toggle like this one.
5. **The on-demand check is the primary path; the nightly sweep (`pg_cron`) is a secondary, separately-shipped enhancement over the identical detection code** — decided with the human specifically so the feature is useful the moment it ships, not gated on `pg_cron`'s own availability (project/tier-dependent on hosted Supabase, and not guaranteed present in every local dev Postgres image). Shipped in its own migration, `20260924030000_scheduled_duplicate_checks.sql`: `atlas.run_scheduled_duplicate_checks()` (never client-callable — no `authenticated` grant at all) loops every model with the toggle on, isolating one model's own failure from the rest of the sweep, calling the identical `atlas.run_duplicate_check` RPC the "Check now" button calls. Availability was confirmed on the live "Architecture" project first (`pg_cron` 1.6.4, read-only check, no write made to that project) before this migration was written, per this item's own caution above; local availability wasn't independently exercised in the authoring sandbox (no Docker route to `pnpm db:start`, the same gap named throughout this sprint) — expected to work there too, since the local CLI's Postgres image bundles `pg_cron` identically, but flagged rather than asserted.

Merge itself needs no new mechanism — a report row's "Merge into…" launches the same `MergeIntoAction`/`atlas.merge_elements` path the "Amended (E7, ...)" paragraph's own item 4 already closed, pre-filled via a URL search-param convention (`src/ui/duplicates/mergePrefill.ts`) matching `decisionPrefill.ts`'s own. ## ADR-020: Capability `code` is a user-set reference, never seed-populated

**Context.** `src/db/seedFromMap.ts`'s `buildSeedDeltas` set `attributes.code = item.code` unconditionally on every capability created from a starter map — duplicating the template's own code as a "fact" asserted about the model's own element. But the template's code was already recoverable two other ways with no duplication: `attributes.templateRef` (`capability_map_items.id`) links back to the template item itself, and the seed commit's own `template_code` alias (`aliases.alias_type = 'template_code'`, SPEC §3.5/ADR-001) records the exact code value used at seed time, surviving even a later rename (ADR-000's own "Tailoring" note on this same alias). Sprint U4-2a's check C1 (`docs/CHECK-U4-2a.md`) named the resulting state directly: `code` displayed unconditionally in the read-only Attributes list (labelled "Code," reading as a stable identifier rather than what it actually was), pre-filled on every seeded capability whether or not the organisation ever gave it independent meaning, and shown as a bare "—" rather than omitted on the (far more common, post-Sprint-U4-1-C5) case of a hand-added capability that was never seeded at all.

**Decision.** `code` becomes an ordinary, optional, user-set reference — relabelled "Reference" (`AttributeFieldMeta.label`, `src/contracts/attributeSchema.ts`) — for an organisation's own use (an internal capability-catalog number, a cross-reference into another system), never populated by `atlas.seed_from_map`/`buildSeedDeltas` at seed time. A capability's template code, when it has one, stays reachable exactly as before through `attributes.templateRef` and its `template_code` alias — neither changes. The read-only Attributes list hides the Reference row entirely when it has no fact (`AttributeFieldMeta.hideWhenEmpty`, `ElementPage.tsx`'s `AttributesTable`), rather than showing "—" — the one deliberate exception to §4.3's "a gap made visible, never hidden" rule: an unset Reference isn't a gap in what's known about the capability, it's a field the organisation hasn't chosen to use yet, the same distinction `templateRef`'s own `hidden: true` already draws for a different reason (ADR-000's Sprint U4-1 D2 note, above).

A one-off backfill (`scripts/stripSeedCodes.ts`, model-scoped, same shape as `scripts/syncDescriptionsFromMap.ts`) commits an `element.update` clearing `code` for every existing capability whose current `code` still equals its own template item's code — i.e., no organisation has ever actually changed it, so the value is pure seed leftover, not a real fact anyone asserted independently. A capability whose code was edited after seeding, to any value (including, coincidentally, the same one), is left untouched: that's now a real, deliberate fact with its own provenance, not seed noise, and this backfill has no way to distinguish "never touched" from "re-entered the same value" without also erasing the latter's legitimacy — it accepts that one is the safe reading and the target.

**Alternatives rejected.**
- *Keep pre-filling `code` at seed, only hide it once redundant* — still writes a duplicate fact on every one of potentially thousands of seeded capabilities for a value already recoverable via `templateRef`/the alias, and gives the field two silently different meanings (seed leftover vs. a real organisation-entered value) with no way to tell them apart in storage.
- *Drop `code` from `CapabilityAttributes` entirely* — an organisation legitimately wants its own reference numbers for some capabilities (a cross-reference into a separate catalog, a procurement code) independent of any starter map; removing the field removes that, not just the seed-populated case this decision actually objects to.
- *Show "—" for an empty Reference like every other optional field* — was the status quo (§4.3's own default). A field that's empty on the large majority of capabilities by design (every hand-added one, and every seeded one nobody has given an organisation-specific reference yet) reads as clutter under that default, not a gap worth flagging the way a genuinely-unset `System.vendor` is.

**Consequences.** `src/contracts/delta.ts`'s `CapabilityAttributes.code` doc comment is corrected: an organisation's own optional reference, never populated by seeding (was: "Reference code from a starter capability map"). `docs/SPEC-data-model.md` §5.1's seeding description and its RT-4 property-test row (§10) are corrected to no longer claim a seeded capability has `attributes.code` set — only `attributes.templateRef` and the `template_code` alias, which RT-4 already checked independently. No schema/migration change: `code` was already an optional JSONB attribute key, not a column: only the write path (seeding) and the read-only display (`hideWhenEmpty`) change.
