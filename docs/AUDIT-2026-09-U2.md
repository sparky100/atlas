### 3.2 Delta union kinds and fold/invert exhaustiveness

The `Delta` union (`src/contracts/delta.ts:290-292`) has exactly 8 kinds:

| # | Kind literal | Declared at |
|---|---|---|
| 1 | `element.create` | `delta.ts:203` |
| 2 | `element.update` | `delta.ts:217` |
| 3 | `element.retract` | `delta.ts:228` |
| 4 | `element.restore` | `delta.ts:237` |
| 5 | `relationship.create` | `delta.ts:249` |
| 6 | `relationship.update` | `delta.ts:262` |
| 7 | `relationship.retract` | `delta.ts:273` |
| 8 | `relationship.restore` | `delta.ts:280` |

`apply` (`src/engine/deltas.ts:162`) is a single `switch (delta.kind)` with no `default` clause and a case for every one of the 8 kinds (`deltas.ts:164,180,196,205,238,256,265,274`); TypeScript enforces exhaustiveness structurally (the function's `Head` return type forces every branch to return). `fold` (`deltas.ts:313`) is a thin loop calling `apply` once per delta with no per-kind logic of its own.

`invert` (`src/engine/deltas.ts:380`) also exists, is not part of SPEC-data-model.md by the file's own comment ("the spec's delta model is append-only by design and has no designed 'undo'"), and is likewise a default-less `switch` covering all 8 kinds (case labels at `deltas.ts:382,384,402,404,406,408,422,424`), mapping each kind to its inverse kind (e.g. `element.create → element.retract`).

Two distinct exhaustiveness proofs exist:
1. **Contract level** — `src/contracts/delta.property.test.ts`: `generatorsByKind` is typed `Record<DeltaKind, fc.Arbitrary<Delta>>` (compile-time exhaustiveness), and the test `'covers every DeltaKind at least once across a real sample (not just in principle)'` runs 500 samples through `deltaArb` and asserts the observed kind set equals `Object.keys(generatorsByKind)`. This file proves exhaustiveness for `toDeltaRow`/`fromDeltaRow`/JSON only — it never imports `src/engine/`.
2. **Engine level** — `src/engine/deltas.property.test.ts`: `fixturesByKind` is typed `Record<DeltaKind, () => KindFixture>`; the describe block `'every DeltaKind: apply + invert (exhaustive over DeltaKind at compile time)'` loops `Object.keys(fixturesByKind)` and, for each kind, folds one delta, inverts it, checks the inverse's `kind`, folds the inverse, and asserts value-level equality with the starting head. A companion test pins `Object.keys(fixturesByKind).length === 8`. This is **fixture-based, not generative** — one hand-written delta per kind, not fast-check-driven; the file's own fast-check properties above it generate only `element.create`/`element.update` deltas and never touch a relationship kind.

## 4. Engine and data path

### 4.1 Call path for an edit on `main`, UI event to rows written

1. **UI event**: a Save click in the element page's attribute editor is handled by `useElementEditor.save()` (`src/ui/elements/useElementEditor.ts`).
2. `save()` validates changed fields via `validateAttributeValue` (`src/contracts/attributeSchema.ts`), gets/creates the user's manual `sources` row via `getOrCreateManualSource` (`src/db/sources.ts`), builds one `element.update` `Delta` per changed attribute, and assembles a `CommitEnvelope` (`src/contracts/delta.ts`).
3. It calls `commitToBranch()` (`src/db/commits.ts`), passing `expectedHeadCommitId` (the commit the page believes is main's current head — the optimistic-concurrency check, C13).
4. `commitToBranch()` runs `shapeErrors()` (structural checks C1/C4/C14), loads the model's full commit/delta history via `buildCommitLoader()` (`src/db/commitLoader.ts`), computes the current head via `foldFromGenesis()` (`src/engine/head.ts`), then computes the **new** head by calling `fold(cloneHead(currentHead), envelope.deltas, ctx)` (`src/engine/deltas.ts`) — this is where the resulting head is computed, and it happens **client-side, in TypeScript**, not in SQL (ADR-015's own text: "The current design computes the resulting `Head` client-side and ships it as data, not as SQL to execute").
5. It serialises the new head via `serializeHeadProjection()` (`src/engine/projection.ts`) into `{ elementsHead, relationshipsHead, facts }` row arrays, and computes `headHash(newHead)` (`src/engine/head.ts`).
6. It calls `supabase.rpc('commit_deltas', {...})`, invoking the SQL function `atlas.commit_deltas` (`supabase/migrations/20260906090000_facts_and_commit_deltas.sql`) with the delta rows and the full serialised projection as jsonb.
7. `atlas.commit_deltas` (security definer): checks role (`atlas.has_role`), inserts the `commits` row, inserts every `deltas` row, advances `branches.head_commit_id` (re-checked by the `branches_guard_head_advance` trigger → `atlas.guard_branch_head_advance`), and — because the branch is `main` — calls `atlas.replace_main_head_projection()`, which deletes and re-inserts the `elements_head`/`relationships_head`/`facts` rows for the new head (and garbage-collects the old head's rows unless a tag protects them).
8. The client's `onSaved` callback (`reload`) re-fetches the page's data (`useElementPage.ts`), rendering the newly-materialised rows.

### 4.2 Head computation location

Client-side (TypeScript), confirmed by (a) `commits.ts` calling `fold`/`serializeHeadProjection` before the RPC call, and (b) ADR-000-foundations.md's ADR-015 section stating this explicitly as "the current design," naming the tradeoff (full projection sent on every commit to `main`, regardless of delta size) and the named upgrade path (delta-apply directly in SQL against existing projection rows), not yet built.

### 4.3 Payload size at 2,000 elements

Documented in `e2e/landscape-perf.spec.ts`'s own code comment: against a fixture of **2,010 elements, 6,000 relationships, ~16,000 facts**, the serialised `commit_deltas` payload for a single attribute edit measures **~8.45 MB**, against a stated budget of **12 MB** (`BUDGET_BYTES = 12 * 1024 * 1024`). The payload-size assertion was run in this environment (it needs no browser or database — pure Node, real `fold`/`serializeHeadProjection`) and passed. The exact current byte count was not independently re-derived outside the Playwright run for this audit (a standalone Node re-derivation attempt failed on this repo's extensionless TypeScript imports, which plain Node ESM resolution doesn't support without a bundler/test-runner transform); the passing assertion corroborates the comment's ~8.45 MB figure is still under the 12 MB budget, but is not itself a fresh byte-for-byte measurement.

### 4.4 `rebuildHead` + head-equals-fold comparison

Exists. `src/db/rebuildHead.ts` recomputes a model's main head from genesis via `foldFromGenesis` and rewrites the projection via `atlas.replace_main_head_projection` (service-role only). The independent head-equals-fold comparison is asserted in `src/db/repository.integration.test.ts`, test titled `"rebuildHead recomputes main's head independently and matches exactly, byte for byte (SPEC §6.6's head == fold(deltas))"` — it folds from genesis independently of `rebuildHead`, calls `rebuildHead`, and asserts the returned `headHash` and the `elements_head`/`facts` rows match, byte for byte. This test is part of the `*.integration.test.ts` suite (cannot run in this sandbox — no local Supabase reachable); it runs via `pnpm test:integration` locally, and in CI's job named **"Fresh-database migration check and integration tests"** (`.github/workflows/ci.yml`, job id `database`), which applies every migration to a fresh `supabase db reset` database before running it.

A second, related test in the same file — `"createTag refuses a commit whose materialised elements_head has been corrupted (P-7)"` — exercises `src/db/tags.ts`'s `createTag`, which as of this branch's Sprint U2 step 4 work independently re-verifies `fold(commit) == materialised projection` (via `verifyHeadMatchesFold`, `src/engine/head.ts`) before ever inserting a tag row.
