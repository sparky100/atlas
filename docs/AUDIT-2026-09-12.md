## 0a. Standing finding: C19 was never built, and every sprint since ignored the sequencing that required it

ADR-021 §2a (accepted 2026-09-11) states: *"C19, P-30 and the P-2 extension land now, in a PR of their own, before Sprints 7i–7k. The fast-forward fold rule closes the latent `HASH`-incident path... on its own and depends on nothing else here."* It defines **C19 (new, `fold`)**: "a merge commit whose first parent is in the ancestry of its second parent folds to the second parent's state plus its own deltas."

Verified: `grep -rn "C19" -i` / `grep -rln "fast-forward" -i` across `src/`, `supabase/`, `docs/` (excluding ADR-021, ADR-000, and the prompt pack itself) returns **zero hits**. `src/contracts/delta.ts`'s `COMMIT_INVARIANTS` array runs `C1` through `C18` only — no `C19` entry. `src/engine/head.ts`'s `foldFromGenesis` has exactly one code path for a merge commit (always recurse + `exclusive()` + topo-sort + fold) — no ancestry check, no fast-forward branch. `git log --all --grep="C19"` and `--grep="fast-forward"` return only three commits, all documentation (ADR-021 itself and the two prompt-pack-update commits for PR #83). **No implementation PR was ever opened.**

PRs #79 (7i), #80 (7j), #82/#85 (7k), #83, #86, #87, #88, #89 (7l) all merged **after** ADR-021's acceptance, without C19 ever landing — directly contradicting the ADR's own "land now... before Sprints 7i–7k" sequencing. This is a standing, unaddressed engine gap in a shipped, in-use merge path.

## 0b. Standing finding: the deploy pipeline has never once succeeded

`.github/workflows/deploy-migrations.yml` is the **only** GitHub Actions workflow in this repository (`list_workflows` confirms one workflow, created 2026-09-09). It runs `supabase link` → `db push` → POST `CLOUDFLARE_DEPLOY_HOOK` on every push to `main`, since Cloudflare Workers Builds' own auto-deploy was turned off (README, "as of Prompt 7g's A3 close-out").

**All 59 runs to date have failed** (run #1, 2026-09-09T12:39Z, through run #59, 2026-09-12T04:01Z — the run for this session's own PR #89 merge). 0 successes, 0 partial. The job log for run #59 (job id 103494694274) shows the exact, consistent failure point: step 4, "Link the Supabase project," every time:

```
Authorization failed for the access token and project ref pair: {"message":"Your account does not have the necessary privileges to access this endpoint..."}
```

`SUPABASE_ACCESS_TOKEN`/`SUPABASE_PROJECT_ID` **are** set (present, masked, in the log) — this is a token-privilege problem, not a missing-secret problem, a more specific diagnosis than README's own troubleshooting note anticipates ("until they're set, the job fails fast"). Because "Push new migrations" and "Deploy the app (Cloudflare)" are later steps in the *same* job, **both are skipped on every single run** — meaning no push to `main` has ever deployed the frontend via this pipeline, independent of whether that push needed a migration.

**Consequence for every "deployed_to_dev" answer below:** the sub-audits in §1 judged "deployed" purely by migration-liveness (per this orchestrator's own instruction to them, given before this full picture was confirmed). That rule is necessary but not sufficient — it tells you whether the *database* is compatible, not whether the *frontend code* is actually being served. **Read every "deployed: yes" in §1 as "present on `main` and not blocked by a missing migration," never as "confirmed running in a browser at atlas.simmodlr.app."** Whether Cloudflare Workers Builds' own auto-deploy was still active for the very earliest of these merges (before the dashboard toggle was flipped) cannot be determined from this repository; nothing after that cutover has a confirmed deploy.
