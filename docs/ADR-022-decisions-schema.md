# ADR-022: Decisions schema extended for prompt pack F0/F3

**Status:** Accepted 2026-09-13 — migrated in `supabase/migrations/20260913110000_decisions.sql` (PR4 of the F0+F3 sprint).
**Numbering:** ADR-021 is the current highest (`docs/ADR-021-structural-conflict-resolution.md`), so this is ADR-022. `docs/ADR-000-foundations.md`'s own index gains a one-line pointer to this file, per that document's established convention for ADR-021 and every later one.
**Depends on:** ADR-013 (`docs/ADR-000-foundations.md`, "Decisions and evidence" — the schema this ADR extends, not replaces), `docs/SPEC-data-model.md` §3.8 (the already-corrected `decision_links.linked_type` value list), F0 (`branches.intent` — an option is an `explore`-intent branch), ADR-010 (the polymorphic-anchor pattern `decision_links` mirrors).

## Context

ADR-013 ratified a `decisions`/`decision_arguments`/`decision_links`/`assumptions`/`evidence` shape but was never migrated — its own Consequences section named the reason: "the workflow... needs its own follow-up ADR once the UI is designed." Prompt pack F3 ("decisions and options") is that UI: a decision is where a problem or opportunity turns into a compared set of options, one of which becomes a real proposed change. Building F3 surfaced two gaps ADR-013's original field list didn't cover, and one already-recorded correction to apply:

1. ADR-013's `decisions` row has no field for who owns driving the decision to a close, distinct from `decided_by` (who actually closed it) — a decision needs an owner from the moment it's opened, not only once it's resolved.
2. Nothing records a target date to close by, or which health-finding check prompted the decision, or an optional link to an external Lens map — all named in the F3 prompt's own text but absent from ADR-013's original column list.
3. ADR-013's own `decision_links.linked_type` enum used `'change_branch'`; `docs/SPEC-data-model.md` §3.8 already independently corrected this to `'branch'` when it first transcribed ADR-013's schema, before this ADR or the migration existed. This ADR ratifies SPEC's text as authoritative and closes the discrepancy in ADR-013's own prose.

## Decision

**`decisions` gains four new nullable columns**, none of them replacing an ADR-013 field:

| Column | Type | Purpose |
|---|---|---|
| `owner_id` | `uuid not null references auth.users(id)` | F3's own "owner" — required at creation, distinct from `decided_by`. |
| `needed_by` | `date` | The target date to close by — F3's own creation-form field. |
| `source_finding_key` | `text` | Which health-finding check a "Start a decision" click traced back to (a stable string key, e.g. `'critical-support-end'` — matching `ArchitectHome.tsx`'s own check keys), never a frozen snapshot of computed finding text, since findings are always recomputed live. |
| `lens_map_url` | `text` | F3's own "may cite a Lens map by URL; no shared schema" — a bare column, no FK, taken literally. |

**`decision_links.linked_type` uses `'element' \| 'relationship' \| 'branch' \| 'assumption' \| 'evidence'`** — SPEC-data-model.md §3.8's already-corrected value list, not ADR-013's original `'change_branch'`. **This is F3's whole "options" mechanism**: an option is a `decision_links` row with `linked_type = 'branch'` pointing at an `explore`-intent branch (F0's own `branches.intent`). There is no separate `decision_options` table — an option is not a distinct concept from a link, it is a link of a particular kind to a branch of a particular intent.

**`decisions.status` transitions are RPC-only past creation.** A decision is created `proposed` (the only status a plain insert may set — `decisions_insert`'s own `WITH CHECK`); `status`/`decided_by`/`decided_at`/`branch_id`/`superseded_decision_id` are set only by `atlas.choose_decision_option` (a later PR in this same sprint — see "Deferred" below). Unlike `branches.intent`'s own guard trigger (F0) — which narrows a *grantable* column's own update window with both a grant list and a trigger — these five columns are never granted to a plain client at all, the same "sensitive column simply isn't grantable" shape `branches.status` itself already uses (no plain-update grant, no guard trigger for it either; only RPCs touch it). `atlas.guard_decision_update` only gates *when* the grantable columns (`title`/`statement`/`owner_id`/`needed_by`/`source_finding_key`/`lens_map_url`) may change by plain update — while `status = 'proposed'` — which also lets `choose_decision_option`'s own `security definer` write through cleanly, since that RPC's transition runs while `old.status` is still `'proposed'`. Once a decision leaves that status (accepted, rejected, or superseded), its own record is closed, matching ADR-013's "a decision is never deleted, only superseded" append-only stance extended to its ordinary fields too.

**Review weight is unaffected by this ADR.** F0's decision that `record`/`correct` branches merge in one click while `propose`/`explore` use the shared queue (a separate, already-resolved decision — see `docs/UI-principles.md` §10, decision 13) applies identically to a decision's chosen option branch once it becomes `propose`-intent: nothing here creates a second review mechanism.

## Alternatives rejected

- *A separate `decision_options` table, each row naming a branch explicitly.* `decision_links` already models "this decision points at that thing" polymorphically (ADR-010's own pattern for comment anchors); a second table for the one case where the linked thing happens to be a branch would duplicate that mechanism for no real gain, and would need its own RLS/insert-gating rules identical to `decision_links`'s own.
- *A `target_date`-shaped reuse of `branches.target_date`, the way F0 reuses that column for `record`'s "delivered date" and `propose`'s "target date".* `needed_by` names when the *decision* should close, not when the *eventual change* should ship — a decision can easily need closing well before its chosen option's own change is scheduled to land, so collapsing the two into one column would conflate two genuinely different dates.
- *Storing `source_finding_key` as a foreign key into a `health_findings` table.* No such table exists — findings are computed live from `elements_head`/`relationships_head`/`branches`, not persisted rows (`src/db/healthFindings.ts`). A stable string key is the only thing that can survive the finding being recomputed differently later without going stale the way a row reference to a since-deleted computation never existed for would.

## Consequences

`src/db/types.ts` gains `DecisionRow`/`DecisionArgumentRow`/`DecisionLinkRow`/`AssumptionRow`/`EvidenceRow` and their enum types (`DecisionStatus`/`DecisionArgumentStance`/`DecisionLinkedType`/`AssumptionStatus`/`EvidenceKind`) — workflow/tenancy row shapes, so they live in `src/db/types.ts`, not `src/contracts/` (that directory is delta/commit/invariants only, per its own module comment — the same split F0's `BranchIntent` already follows). `docs/SPEC-data-model.md` §3.8 is updated to list the four new `decisions` columns explicitly rather than only "column lists as in ADR-013."

**Closed by PR5, `20260913120000_choose_decision_option.sql`:** `atlas.choose_decision_option` (sets `status`/`decided_by`/`decided_at`/`branch_id`, inserts the one `decision_arguments` reasons row, flips the chosen branch's own intent to `propose`, and cancels every other `branch`-linked option still in `draft`), the comparison table (`src/ui/decisions/compareOptions.ts`), "Add an option," and "Choose" (`src/ui/decisions/useDecisionOptions.ts`). One correction PR5 made to this ADR's own original text: `atlas.guard_decision_update` does **not** enforce a column allow-list via the trigger — that would have blocked `choose_decision_option`'s own legitimate write to `status`/`decided_by`/`decided_at`/`branch_id` (a bug caught before it ever ran a real migration). Those five columns are simply never granted to a plain client at all — the same "sensitive column isn't grantable" shape `branches.status` itself already uses — and the trigger only gates *when* the grantable columns may change (`status = 'proposed'`).

**Closed by PR6, the sprint's last PR:** "Start a decision" from a health finding — `HealthFinding.tsx`'s own new per-row action slot, wired into `ArchitectHome.tsx`'s `critical-support-end` Assurance check (F3's own named "SAP PM" golden path) and, separately, into `DirectorHome.tsx`'s weak-capability tile (F3's second named golden path) — both hand `/decisions` a pre-filled form via ordinary URL search params (`src/ui/decisions/decisionPrefill.ts`), never router state, so the link is real and shareable. "Why is this here" — `ElementPage.tsx`'s "Decisions" section, previously a hardcoded `<EmptyState>` (Prompt 7h bug B6, predating this schema), now queries `decision_links` for `linked_type='element'` matching the element itself and, for a capability, its own capability ancestors (`src/db/decisions.ts`'s `listDecisionsLinkingElements`, `src/ui/components/ElementDecisionsSection/`) — showing each decision found plus its options, the chosen one and every cancelled "losing" one alike. ADR markdown export — `src/ui/decisions/exportDecisionAsAdr.ts`, a pure string-template builder (`exportCapabilityMap.ts`'s own "read the model, walk it, produce output" shape, writing text instead of JSON), copied to the clipboard from `DecisionView.tsx`'s "Copy as ADR markdown" the same way `ElementHeader.tsx`'s own "Copy element ID" already does — no file-download mechanism exists anywhere in this app to invent a second one for.

One deliberate scope narrowing within PR6, recorded here rather than left silent (CLAUDE.md rule 7): "Start a decision" reaches the director door's own weak-capability tile and the architect door's health-finding row (F3's own two named golden paths, both built) but not yet the capability map's own L2/L3 tiles (`CapabilityMapView.tsx`'s shared `CapabilityTile.tsx`, used by `CapabilityMapPage.tsx`) — that component has no `role` prop at all today, and its colour-by/reorder/expand state is already tightly coupled; adding a third entry point there is real, separable work, not a one-line addition. Unscheduled — see `docs/SPEC-data-model.md` §11.

**Deferred, unscheduled — not part of this sprint's own plan:**
- Any authoring UI for `assumptions`/`evidence` — CLAUDE.md rule 7: the tables ship schema-complete, since `decision_links` needs both as legal link targets, but nothing writes to them yet beyond a plain insert grant no UI currently calls.
- The "re-review nudge" (`assumptions.linked_review_pending`, set when an assumption's own status changes) — the column exists so nothing reading it later needs a migration to add it.
- "Start a decision" on the capability map's own L2/L3 tiles (see above).
